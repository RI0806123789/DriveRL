# DriveRL

現実の道路マップ（OpenStreetMap）上で、**マルチエージェント強化学習（MARL）で走る複数の自動運転車**を
リアルタイムに学習させながら 3D で鑑賞・介入できるシミュレーターです。

学習は**表示中も裏で進み続けます**。ブラウザに映っているのは学習済みモデルの再生ではなく、
いま重みが更新されている最中のポリシーの挙動です。

車両は**車載カメラ相当の映像を CNN で認識した結果だけを見て走ります**。
信号の灯色も、速度標識の数字も、車線も、前の車も、すべて画像から検出したものです。
**認識を誤ればそのまま赤信号へ突っ込みます**（衝突や信号無視の判定はシミュレーター側が
正しく行うので、認識できなかったから見逃される、ということはありません）。
運転席カメラに切り替えると、**いま何を認識しているのかがバウンディングボックスで見えます**。

- **バックエンド**（Python / FastAPI）— OSM の道路網を走行可能なトポロジへ変換し、
  擬似カメラ映像を CNN（Keras 3）で認識させ、その結果を入力に自作 PPO で
  複数車両を同時に学習させる。物理・衝突判定・信号制御もここで行う。
- **フロントエンド**（React / TypeScript / Three.js）— WebSocket で受け取った状態を 3D 空間に描画し、
  クリックで障害物設置や車両追加といった介入を行う。

## できること

| | 内容 |
|---|---|
| **現実の地図** | 東京・銀座 / 大阪・梅田 / 名古屋・栄 / 石川・金沢 の 4 プリセット。道路・建物・信号機を OSM から取得 |
| **画像認識で運転** | 擬似カメラ映像を CNN（Keras 3 / torch バックエンド）で認識し、信号の灯色・規制速度・車線・車両・障害物・歩行者を検出。**その検出結果だけを見て走る** |
| **認識の可視化** | 運転席カメラで、認識したものにバウンディングボックスと名称（「信号機：青」「速度標識：40km/h」「車線」）を重ねて表示 |
| **オンライン学習** | 自作 PPO（PyTorch, CPU）。全車両が同一の重みを共有（parameter sharing）|
| **交通ルール** | 左側通行・車線走行・右左折時の寄せ・赤信号での停止（いずれも日本の道路交通法に準拠）|
| **3D 描画** | 道路標示・信号機・建物・車両。俯瞰／追従／運転席の 3 カメラ |
| **街を歩く歩行者** | 最大 64 人の NPC が歩道を歩き、**歩行者用信号に従って**横断する。擬似カメラにも映り、観測・衝突判定にも入る |
| **車両のライト** | 前照灯・尾灯・制動灯・方向指示器。夜と雨・霧で点灯し、右左折の 30m 手前からウインカーを出す（道交法 52 条・施行令 21 条）|
| **ナンバープレート** | 日本の中型・自家用（白地に緑文字）。**地名は走っている街に合わせる**（銀座→品川 / 金沢→石川）|
| **昼と夜** | 走らせている街の**日の出・日の入りに合わせて画面全体の配色が切り替わる**。設定項目は無い |
| **天候** | 雨と霧。**擬似カメラと 3D 画面の両方に効く。** 霧は視程を縮め、遠くのものは正解ラベルからも外れる。時間で自動に移り変わらせることもできる |
| **弱点の自動収集** | 教師データを集める前に**いまの認識器を採点**し、成績の低いクラス・天候を多めに集める（アクティブラーニング）|
| **介入** | 走行中にクリックで障害物設置・車両追加。置いたパイロンはクリックで 1 個ずつ撤去。学習は止まらない |
| **モデルの入出力** | 学習済みモデルの書き出し（.pt / TorchScript / .keras）と、読み込みによる学習再開 |
| **認識器の学習** | **画面の「モデル作成」タブから CNN を学習できます。** 教師データの収集から保存・載せ替えまで、コマンドを叩かずに完結します |
| **自動運転タクシー** | **実用モード**に切り替えると、学習済みの重みで走る街に降り立ち、スマホ画面からタクシーを呼べます。歩いて乗り込み、目的地まで乗って降りるところまでを一人称で体験できます |
| **PWA** | ブラウザからインストールして**全画面のアプリとして起動**できます（アドレスバーもタブも出ません）|

### プリセットの規模

| エリア | 範囲 | 交差点ノード | 道路セグメント | 建物 | 灯器 | 標識 | 道路総延長 |
|---|---|---|---|---|---|---|---|
| 東京・銀座 | 0.8km 四方 | 168 | 293 | 1,299 | 261 | 136 | 19 km |
| 大阪・梅田 | 0.9km 四方 | 49 | 93 | 315 | 73 | 54 | 8 km |
| 名古屋・栄 | 0.9km 四方 | 94 | 168 | 798 | 151 | 91 | 13 km |
| **石川・金沢** | **12.3km 四方** | **19,493** | **58,120** | **35,607** | **2,736** | **15,719** | **4,346 km** |

**金沢だけ規模が 2 桁違います。** 他の 3 つは「碁盤目状の街路 + 高密度な建物」という
学習題材として素性の良い区画を切り出したものですが、金沢は**市街地の全域**（12.3km 四方 =
150km²）を対象にしています。金沢駅・兼六園・野々市市境・金沢港の手前までが入ります。

灯器の数え方も金沢だけ違います。他の 3 つは **OSM のタグではなく接続道路 3 本以上のすべての
交差点に信号を置いて**います（`loader.SIGNALS_AT_ALL_INTERSECTIONS`）。OSM のタグ通りにすると
銀座 51 / 梅田 16 / 栄 91 まで減りますが、無信号交差点だらけの街になります。
代償として信号の間隔が詰まり、平均速度は 4.5 km/h まで落ちます（時間の 57.6% が停止）。
**金沢は広域なのでタグ通り**にしてあります。全交差点に置くと 55,714 基になり、
`frame.signals` が毎フレーム同じ長さの配列を送る仕様のため配信量が 2.4MB/s に達するためです
（タグ通りなら 2,736 基 = 0.40MB/s）。

**街路の性格も金沢だけ違います。** 城下町の街割りが残っており、**十字路より T 字路が
3 倍近く多い**低連結の道路網です。碁盤目の 3 都市で学習した方策がそのまま通用するかを
見る対照として入れてあります。

| | 十字路（4 本）| T 字路（3 本）| 行き止まり | 5 叉路以上 | 直角に近い交差 | 平均接続本数 |
|---|---|---|---|---|---|---|
| 東京・銀座 | 71 | 65 | 7 | 2 | 51.0% | 3.23 |
| 大阪・梅田 | 13 | 19 | 3 | 2 | 26.8% | 2.98 |
| 名古屋・栄 | 38 | 40 | 2 | 0 | 62.2% | 3.21 |
| 石川・金沢 | 4,510 | **13,027** | 1,393 | 51 | 44.3% | 3.07 |

> **金沢は目的地が遠くなりがちです。** 出発地と目的地は「120m 以上離れていればどこでもよい」
> という選び方だったので、12.3km 四方のマップでは無作為に選んだ 2 点が平均 6km 離れました。
> 1 エピソードは 4,000 ステップ（200 秒）で、**一度も止まらず最高速 50km/h で走り続けても
> 2,780m** しか進めないため、実測した経路 120 本のうち **80% が物理的に到達不能**でした
> （銀座は 0%）。いまは `world.ROUTE_MAX_DISTANCE_M`（3km）を `random_node_pair` へ渡して
> **39% まで下げてあります**（同じ測り方で 120 本）。経路が短くなったぶん再スポーンも軽く
> なりました（金沢で 1 回 58.4ms → 9.0ms）。**銀座は 0.8km 四方なので上限に掛からず、
> 何も変わりません。**

## セットアップ

前提: **Python 3.13** と **Node.js 22.18 以降**。CUDA 対応 GPU は不要（CPU で学習します）。

Node に 22.18 以降が要るのは、`npm run verify` が `node scripts/verify-*.ts` の形で
**TypeScript をそのまま実行する**ためです（型注釈の除去が既定で有効になったのがこの版）。
動作確認は Node 24.16 / npm 11.13 で行っています。

### バックエンド

```powershell
cd "C:\Users\<ユーザー名>\Documents\GitHub\DriveRL"
py -3.13 -m venv backend\.venv
backend\.venv\Scripts\python.exe -m pip install --upgrade pip
backend\.venv\Scripts\python.exe -m pip install -r requirements.txt
```

`requirements.txt` の先頭にある `--extra-index-url https://download.pytorch.org/whl/cpu` は
**消さないでください**。CPU 版 PyTorch（`torch==2.14.0+cpu`）は PyPI に無いため、
この行が無いとインストールに失敗します。

### フロントエンド

```powershell
cd "C:\Users\<ユーザー名>\Documents\GitHub\DriveRL\frontend"
npm install
```

## 起動

**ターミナル 1 つ、コマンド 1 つで起動します。**

```powershell
cd "C:\Users\<ユーザー名>\Documents\GitHub\DriveRL"
.\run.ps1 -Dev
```

ブラウザで `http://localhost:5173` を開きます。**Ctrl+C で両方まとめて止まります。**

> **`.ps1` の中身がメモ帳で開いてしまうとき**
> PowerShell ではなく **cmd.exe かエクスプローラーから実行しています**
> （`.ps1` は Windows の既定でメモ帳に関連付けられているため）。
> その場合は `run.cmd` を使ってください。
>
> ```
> run.cmd --dev
> ```
>
> PowerShell で「スクリプトの実行が無効」と拒否される場合は
> `powershell -ExecutionPolicy Bypass -File .\run.ps1 -Dev` を使ってください。

> **`ポートが既に使われています` と出るとき**
> すでに起動済みです。ブラウザで http://localhost:5173 を開いてください。
> 窓が見当たらない場合は、表示された `taskkill` の行をそのまま実行してから
> やり直してください。

起動したら右パネルの「マップ」タブでプリセットを選んでください。読み込みが終わると学習が始まります。

### 起動モードは 3 つ

cmd.exe やエクスプローラーからは `run.cmd --dev` / `run.cmd` / `run.cmd --build` と読み替えてください。

| コマンド | 何が動くか | ブラウザで開く | 向いている場面 |
|---|---|---|---|
| `.\run.ps1 -Dev` | バックエンド + Vite | `localhost:5173` | **開発中。**フロントの変更が保存だけで反映される |
| `.\run.ps1` | バックエンドのみ | `127.0.0.1:8000` | 眺めるだけ。**メモリが 300MB ほど軽い** |
| `.\run.ps1 -Build` | ビルド → バックエンドのみ | `127.0.0.1:8000` | フロントを直した後、軽い方で動かしたいとき |

`-Dev` を付けない場合は `frontend/dist`（ビルド済み）を配信します。dist が無いと画面が出ないので、
その場合は起動時に警告が出ます。

**`-Dev` で動くのは Vite だけです。** バックエンドはリロードしないので、フロントを何度直しても
**学習の途中経過は失われません**。逆にバックエンドを直したときは Ctrl+C で止めて起動し直す必要があります
（`--reload` を使わないのは、リロードのたびに学習スレッドが作り直されるためです）。

<details>
<summary>PowerShell 以外から起動する / 個別に動かす</summary>

`run.ps1` / `run.cmd` は venv のパスを埋めるだけの薄いラッパーで、
中身はどちらも `backend/run.py` です。

```powershell
backend\.venv\Scripts\python.exe backend\run.py --dev
```

従来どおりターミナルを 2 つ使う方法も残っています。

```powershell
cd backend;  .venv\Scripts\python.exe run.py     # 1 つ目
cd frontend; npm run dev                          # 2 つ目
```
</details>

**バックエンドを起動せずにフロントだけ触る**こともできます。`npm run dev` で開いた URL に
`?mock=1` を付けると、`store/mockServer.ts` が frame / metrics / network と、認識器の学習、
実用モードの配車（迎車 → 乗車 → 到着 → 降車）まで返します。見た目と画面遷移の確認に使えます
（**開発ビルドのみ**。本番ビルドでは常に無効です）。実物のモデルが無いので、
モデルの書き出しと読み込みだけは塞いであります。

## アプリとしてインストールする（PWA）

ブラウザのタブではなく、**独立した全画面のウィンドウ**で動かせます。
`run.ps1 -Build`（または `-Dev` 以外）で起動して <http://127.0.0.1:8000> を開き、

- **Chrome / Edge**: アドレスバー右端のインストールアイコン、または
  「⋮」メニュー →「アプリとしてインストール」（「キャスト、保存、共有」の中にある場合もあります）

を選ぶとインストールされます。以降はスタートメニューやタスクバーから起動できます。

| | |
|---|---|
| 表示モード | `fullscreen`（全画面）。対応していない環境では `standalone` → `minimal-ui` の順に落ちます |
| 起動 URL | `/`（バックエンドが 127.0.0.1:8000 で動いている必要があります）|
| アイコン | 192 / 512 px と Android 用の maskable。`npm run icons` で作り直せます |

> **Windows のデスクトップ版 Chrome は `fullscreen` を standalone 相当（枠なしウィンドウ）で
> 開くことがあります。** その場合は **F11** で全画面になります。Android / Chrome OS では
> 指定どおり全画面で起動します。

**オフラインでは動きません。** 走行も学習もバックエンド（FastAPI + PPO スレッド）の中で
起きていて、画面は WebSocket で受け取ったものを描いているだけだからです。
インストールしておくと**画面の枠（HTML と JS/CSS）だけ**はキャッシュから即座に開き、
バックエンドが起動していなければ「バックエンドに接続していません」と表示されます。
`backend/run.py` を起動すれば**リロードせずに自動で再接続**します。

- **キャッシュするのは画面の枠だけです。** `/api/`（モデルの書き出し・読み込み）と
  WebSocket は Service Worker が一切触りません
- HTML は必ずサーバーへ問い合わせます（キャッシュを先に返すと、再ビルドしたのに
  消えた JS を指したままの画面が出るため）
- 画面が古いまま直らないときは、`frontend/public/sw.js` の `CACHE_VERSION` を上げて
  ビルドし直してください

## 画面の見かた

3D のシミュレーターが画面全面、その右上に操作パネルが角丸のカードとして浮かんでいます
（カードの周囲には 3D が透けて見えます）。
走行状況はそのカードの**真下**に、**カードと同じ幅**で 1 行に並びます。

パネルの幅は「走行状況が 1 行に収まる幅」から逆算しています
（`frontend/src/styles/tokens.css` の `--m3-hud-oneline`。実測値と測り方をそこに書いてあります）。
チップの文言や枚数を変えたら、その値を測り直してください。
右パネルはハンバーガーボタン、または **M キー**で畳めます。畳むと画面は 3D だけになります
（ブランド名と右下の走行状況もパネルと一緒に引っ込みます）。

| タブ | できること |
|---|---|
| シミュレーション | 再生／一時停止、車両数、**歩行者数**、速度、交通ルール、**天候**、介入モード、**車両の追跡** |
| マップ | プリセットの選択と読み込み状況 |
| 学習 | **ネットワークのノード図**、学習指標のグラフ、ハイパーパラメータ、報酬の重み、**隠れ層の構成変更**、モデルの書き出し／読み込み |
| モデル作成 | **画像認識の CNN（認識器）を学習する。** 収集枚数・エポック数・バッチサイズ・モデルの大きさを指定して実行し、進捗と損失をその場で見る。**収集前に測った弱点**もここに出る |
| 表示 | カメラモード、建物・道路標示・信号機・経路などの表示切替 |

**「一時停止」は描画だけを止めます。** 裏側の学習は止まりません。
これは「常にオンライン学習を継続する」という設計方針によるもので、UI にも明示しています。

例外は**「モデル作成」タブで認識器を学習している間だけ**で、このときは走行も強化学習も
止まります（CPU を使い切るため）。完了・中断すると自動で再開します。
止まっていることは「シミュレーション」タブと「学習」タブにも表示されます。

### 画面左上の表示（HUD）

| 項目 | 意味 |
|---|---|
| 走行中 N 台 | いま動いている車両数 |
| 経過 N 秒 | シミュレーション内の経過時間（倍速をかけた後の時間）|
| ステップ N | 物理・学習ステップの累計 |
| 障害物 N | 置いてあるパイロンの数 |
| 受信 N Hz | サーバーからフレームが届いている頻度 |
| 描画 N call | 1 フレームのドローコール数。台数を増やしたときの描画負荷の目安 |
| **実効 N 倍** | 実際に出ている倍速。要求の 9 割を下回ると**警告色**になる |

**「実効 N 倍」は台数を増やすと必ず落ちます。** 倍速スライダーは 8 倍まで動きますが、
上限の 8 台では認識器の推論が効いて 1.6 倍前後で頭打ちになります
（ground truth 観測だった頃は 64 台で 3.2 倍前後でした）。黙って遅くなると
気づけないので、要求値ではなく実測値を出しています。

車両は台数によらず InstancedMesh でまとめて描くので、**台数を増やしてもドローコールは
ほとんど増えません**。増えるのは建物・道路・標示の側です。

### 昼と夜

**画面の配色は、走らせている街の日の出・日の入りで自動的に切り替わります。**
切り替え用の設定項目はありません。時計と暦だけで決まります。

| | 昼 | 夜 |
|---|---|---|
| 空 | 明るい青。遠景は霞む | ほぼ黒 |
| 建物 | 明るい灰。高いほど白く霞む | 暗い青灰 |
| 路面 | 灰（昼でもアスファルトは暗い）| 濃い灰 |
| 白線 | 白 | やや落とした白 |
| 操作パネル | 白地 | 黒地 |

**信号の灯火（青・黄・赤）だけは変わりません。** 現実の信号がそうであるように、
環境によって色が変わっては意味を成さないためです。

基準にするのは**シミュレーターが映している街**です。銀座を走らせていれば東京の、
梅田なら大阪の日の出で切り替わります。同じ日本国内でも銀座と梅田では日の出が
約 18 分ずれるので、そのぶんも反映されます。

計算は緯度・経度と日時だけで完結するので、**外部の API は使いません**。
位置情報の許可も求めません（プリセットの座標がサーバーから届くため）。
マップを読み込む前だけは座標が分からないので、タイムゾーンから経度を逆算して
おおよその値を使います（日本標準時 UTC+9 → 東経 135 度）。

> 一日中同じ配色で使いたい場合、いまのところ切り替える手段はありません。
> 必要なら `src/store/autoTheme.ts` を差し替えてください。

### 車両を追跡する

「シミュレーション」タブの車両一覧をクリックすると、その車両を追跡します。

- 3D 画面でその車両の上に**車両色のピン**が立ちます。建物の陰に入っても見えるので、
  そのまま位置を追えます
- 追従カメラ・運転席カメラの対象にもなります
- 「追跡中の車両」カードに次が出ます

| 項目 | 内容 |
|---|---|
| 車両番号 | スロット番号。車体色の見本が付き、衝突・目的地到達はその場でチップが出ます |
| 車速 | m/s と km/h |
| 目的地まで | 直線距離 [m] |
| 信号無視 | このエピソード中に赤信号で停止線を越えた回数 |
| 車線逸脱 | このエピソード中に車線を外れた回数 |
| 達成度 | 経路上をどこまで進んだかの割合（%）|

車線逸脱は毎ステップの状態ではなく、**外れ始めた瞬間**を 1 回と数えます
（中心から 1.75m 超で「外れた」・1.25m まで戻って「戻った」）。
**速度超過も同じ数え方**で `frame` に入っていますが（規制 +0.5 m/s 超で「超過」・
+0.1 m/s 未満で「復帰」）、標識順守が有効なあいだは 0 のままなので、このカードには
出していません。見たいときは「学習」タブの「速度超過/エピソード」を使ってください。

### 障害物を置く・撤去する

「シミュレーション」タブの「介入」で **障害物を置く** を選び、3D 画面をクリックすると
その地点にパイロンが立ちます（最大 64 個、半径 0.2〜2.0m）。

**置いたパイロンをクリックすると、その 1 個だけが消えます。** 全部消すときは
「すべて消す」を使ってください。パイロンは車両の観測（近傍障害物 3 件）に入るので、
置いた瞬間から学習側の入力が変わります。

## 自動運転タクシーに乗る（実用モード）

操作パネル右上のトグルで、**開発モード**（学習を回す）と**実用モード**
（学習済みの重みで走る街に降りる）を切り替えます。

実用モードに入ると、パネルが**スマホ画面**に変わり、3D は歩行者の**一人称視点**になります。

### 流れ

1. スマホの **タクシーを呼ぶ** を押す
2. 地図をタップして**行き先**（降車地点）を選ぶ。**乗車地点は選びません。
   いま自分が立っている場所が乗車地点です**（実際の配車アプリと同じ）
   （ドラッグで移動、ホイールで拡大。選んだ地点は**最寄りの交差点へ自動で寄せられます**。
   道路の途中は指定できません。そこを目的地にすると、経路が一度通り過ぎてから
   折り返す形になり、タクシーが目的地の前で止まらなくなるためです）
   - 地図は**配車の進み具合に合わせて自動で寄り引き**します。迎車中はタクシーと乗車地点の
     両方が入るところまで、到着したら降車地点まで。自分でドラッグ・拡大すると自動追従は
     止まり、**自動に戻す** が右下に出ます（段階が変わると自動へ戻ります）
   - **乗っている間だけ、地図は進行方向が上を向くように回ります**（カーナビと同じ向き）。
     迎車を待っている間は北が上のままで、目的地に着くと北へ戻ります。
     切り替わりは 1〜2 秒かけて滑らかに回り、**回っている間は右上に北を指す針**が出ます
3. **ここまで呼ぶ** を押すと、いまいる場所にいちばん近い車両が迎えに来ます。
   **自分は動きません**（立っている場所がそのまま乗車地点なので、待っていれば来ます）。
   到着までの時間が出ます
   - 迎えに向かっている車が**来られなくなったとき**（事故を起こした／道が塞がって
     近づけない）は、**配車はそのままで別の車両に切り替わります。**
     **赤信号や前の車で止められている間は「近づけない」に数えません**（赤はひとつが
     30〜47 秒続くので、数えると待っているだけで切り替わってしまいます）
     スマホ画面に「車両 #1 が来られなくなったため、車両 #5 が向かっています」と出て、
     到着時間と経路が引き直されます。切り替えは 3 回までで、それでも届かなければ打ち切ります
   - **乗ってからの事故は切り替えられません**（車内にいるため）。配車を打ち切ります
   - 配車ボタンの下の **カメラ** を押すと、地図の上半分にタクシーの**車載カメラ**が開きます。
     運転席からの眺めに**認識結果のバウンディングボックス**が重なるので、
     迎車を待っている間も「いまタクシーが何を見ているか」を確認できます。
     もう一度押すと閉じます（配車が終わると自動で閉じます）
4. 照準を車に合わせて **[Enter]** で乗車。運転席からの眺めに切り替わります。
   **迎車の途中でも、近づいて照準に入れば乗れます**（乗車地点まで待つ必要はありません）。
   そこから目的地までの経路は、乗った場所を起点に作り直されます
5. 目的地に着いたら **[Enter]** で降車（スマホの「降車する」でも同じ）

### 操作

| キー・操作 | 何が起きるか |
|---|---|
| 3D 画面をクリック | マウスで視線を回せるようになります（ポインタロック）。**[Esc]** で解除 |
| **W / S** | 前進・後退 |
| **A / D** | 左右への平行移動 |
| **[Enter]** | 照準に入っている車両に乗車／降車（迎車の途中でも乗れます）|
| **[Space]** | **緊急停止。** その場で車を止めて自動運転を終了します（乗車中なら降ろされます）|

### 実用モードで止まるもの・止まらないもの

| | 実用モード中 |
|---|---|
| 物理・信号・天候 | **動いたまま** |
| 全車両の走行 | **動いたまま**（経路追従。下記）|
| 重みの更新（学習）| **止まる。** 開発モードに戻すと再開します |

- **実用モード中は、街の車もタクシーも方策ではなく経路追従で走ります。** 学習が進んで
  いないモデルでも必ず迎えに来させるためです。タクシーだけを経路追従にすると、
  止まったままの車が道を塞いでその後ろで詰まるので、街ごと動かしています。
  信号・規制速度・カーブでの減速、前の車との車間はそのまま効くので、
  **赤信号は守りますし制限速度も超えません。** 開発モードに戻すと方策の運転に戻ります。
- 徴用中の車両は、乗降地点に着いても目的地を選び直しません（乗客を置いて走り去らないため）。
  降車すると、その場から新しい目的地へ向かう新しいエピソードとして走行に戻ります。
- **金沢だけは、ごくまれに車どうしが接触します**（実測: 200 秒・8 台で 2 回。銀座は 0 回）。
  12.3km 四方の地図から作った経路に、建物を貫くものや最小旋回半径 4.4m より急な
  カーブが混じるためです。事故に遭うと配車はその場で打ち切られます。
- **エリアの切り替えは開発モードの「マップ」タブから**行ってください。実用モード中は
  スマホ画面だけが出ます（エリアを切り替えると配車は取り消されます）。
- 同時に配車できるのは **1 件だけ**です。

## 画像認識で運転する

車両は**カメラ映像を CNN で認識した結果だけを見て走ります**。信号の現示や標識の
規制速度といったシミュレーター内部の正解値は、走行側には渡していません。

### 何をカメラで見て、何を見ていないか

実車と同じ切り分けにしてあります。

| 経路 | 内容 |
|---|---|
| **カメラ認識（CNN）** | 信号機（灯色）・最高速度標識（規制速度）・車線・前方車両・障害物・**歩行者**・走行可能領域 |
| **車載センサー / ナビ** | 自車の速度と舵角（速度計・舵角センサー）、目的地の相対位置と経路案内（GPS・地図）|

目的地までカメラに探させることはできません（**見えないものは検出できない**ので、
学習が原理的に成立しません）。実車でもナビが経路を与え、カメラは周囲を見ます。

**認識を誤ってもシミュレーターは誤りません。** 赤信号を見落として進めば、判定は
真値で行われるので信号無視として記録され、罰が入ります。「認識できなかったから
見逃してもらえる」ということはありません。

### 車両のライト

車には**前照灯・尾灯・制動灯・方向指示器**が付いています。

| ライト | 点くとき |
|---|---|
| 前照灯（白） | **夜**、または**小雨以上の雨・霧**（道交法 52 条） |
| 尾灯（赤・暗め） | 前照灯と同時 |
| 制動灯（赤・明るい） | **ブレーキを踏んでいる間**（加速度の実測ではなく指令で判断） |
| 方向指示器（橙） | **右左折の 30m 手前から**（道交法施行令 21 条）。毎分 90 回で点滅 |
| ハザード（橙・左右同時） | 実用モードで**乗車・降車を待っている間** |

方向指示器は経路の 30m 先の接線と現在の接線を比べて決めます。出す 0.35rad /
消す 0.12rad のヒステリシスが入っているので、緩いカーブで点いたり消えたりしません。
実測（銀座・8 台・60 秒）では、点灯していた割合が左 9.6% / 右 16.3% / 制動灯 8.3%、
状態の変化は 0.55 回/秒でした。

前照灯とハザードだけはクライアントが決めています。**昼夜はサーバーが持っておらず**
（日の出・日の入りはブラウザ側で計算しています）、配車の段階も画面側の概念だからです。

### ナンバープレート

車の前後に、日本の中型・自家用ナンバープレート（白地に緑文字、330 × 165mm）が付きます。

| 欄 | 中身 |
|---|---|
| 地名 | **走っている街に合わせます**（銀座→品川 / 金沢→石川 / 梅田→なにわ / 栄→名古屋）|
| 分類番号 | `300`（車体は全幅 1.8m で 5 ナンバー枠を超えるため 3 ナンバー）|
| ひらがな | `さ`（自家用。レンタカーの「わ」や事業用の緑地は使いません）|
| 一連指定番号 | **車両番号**。1 桁なので中黒で埋めて `・・・0`〜`・・・7` |

**実用モード（タクシー）の画面は、車をこのプレートで指します**
（「品川 300 さ ・・・0 が迎えに向かっています」）。
開発モードの車両一覧やカメラ選択は、識別しやすさを優先して番号のままです。

車両番号は「シミュレーション」タブの一覧や 3D のピンと同じ番号です。
**プレートは 33cm しかないので、読めるのは近くに寄ったときだけです。**
遠くから車を見分けるには、従来どおり車体の色とピンを使ってください。

### 街を歩く歩行者（NPC）

「シミュレーション」タブの**「歩行者」スライダー（0〜64 人）**で、街に人を出せます。
歩行者は道路に沿った歩道（車道の端から 1.7m）を歩き、**交差点で車道を横断します**。

- 擬似カメラにも映り、正解ラベルも付くので、「モデル作成」タブで学習すると
  **「歩行者」として枠が出るようになります**（検出クラスは 6 種類になりました）
- PPO の観測にも**歩行者の欄（前後・左右・信頼度 × 3 人）**が入り、走行可能領域も
  歩行者で狭まります。**観測は 57 次元から 66 次元に増えたので、
  それ以前に学習した重みは読み込めません**（`warmstart_policy.py` で立て直せます）
- 車が当たれば建物・車両と同じ**衝突**として扱われ、`rewardCollision` の罰が入って
  エピソードが終わります。「学習」タブの**「うち歩行者」**と
  **「歩行者との衝突」のグラフ**で、衝突のうち相手が歩行者だった割合を追えます
- **交差点では歩行者用信号に従います**（「信号機」の節）。赤のうちは渡り始めません。
  見るのは**その道を走ってくる車の信号**で、車が赤なら渡ってよい、という裏返しです
  （銀座では歩道の端 542 か所のうち 462 か所に信号が結び付きます。実測 300 秒で
  横断 105 回・信号待ち最長 25.4 秒・赤のうちに渡り始めた回数 0）
- 実用モード（自動運転タクシー）では、**前方の歩行者の 4.5m 手前で止まります**
  （前走車との車間と同じ式。実測で 4.75m 手前に停止）。
  学習中の車には掛けないので、PPO から見た環境は変わりません
- ★ **あなたが操作する徒歩キャラも、この「歩行者」に含まれます。**
  実用モードの間だけ位置がサーバーへ送られ（`player_pose`）、NPC と同じ 1 人として
  街に立ちます。目の前に立てば車は止まり（実測: 8.33 m/s から 4.50m 手前で停止、
  どいたら再発進）、飛び出せば**事故として扱われます**（迎車中なら別の車へ引き継がれる）

★ **どの車からも 220m 以上離れた歩行者は、見えないところで車の近くへ回されます。**
これが無いと広いマップでは 1 人も画に写りません（金沢は 12.3km 四方なので、
64 人を一様に撒くと 0.42 人/km² にしかならず、実測で真値 0 件でした）。

### 天候（雨と霧）

「シミュレーション」タブで**晴れ / 小雨 / 雨 / 霧 / 濃霧**を選べます。
「時間で自動に変える」を入れると、シミュレーション内の時刻に沿って
晴れ → 雨 → 晴れ → 霧 と 8 分周期でゆっくり巡ります（昼夜の自動切り替えと同じ発想）。

雨と霧は**役割が違います**。

| | 何をするか | 視程 | 認識への効き方 |
|---|---|---|---|
| **雨** | 画を暗く濁らせ、斜めの筋を乗せる | 縮めない | 晴れで学習した認識器でも**ほぼ無傷**（実測 78.8%）|
| **霧** | 距離に応じて白く沈ませる | **縮める** | 晴れで学習した認識器は**崩れる**（実測 11.5%）|

**霧で視程が縮むと、正解ラベルも同じ距離で打ち切られます。** 見えないものを当てさせると
認識器から見てタスクが定義できないためで、擬似カメラの描画と正解ラベルは
`percep/weather.py` の `visibility_m()` という**同じ 1 つの値**を使っています。
いま効いている視程は「シミュレーション」タブに出ます（濃霧で 18m、霧で 37m、晴れで 120m）。

**観測だけが濁り、報酬と終了条件は真値のままです。** 霧で赤信号を見落として進めば、
そのとおり信号無視として記録され、罰が入ります。

**3D の画面にも同じ天候が描かれます。**

| | 見た目 |
|---|---|
| 雨 | 空が暗く濁り、**太さと速さの違う 3 層**の筋が風で斜めに降る。強いほど密になる |
| 霧 | 遠くが白く（夜は暗く）沈む |
| 路面 | 雨で濡れて暗く沈み、つやが出る。**雨がやんでも十数秒は濡れたまま**で、ゆっくり乾く |

天候の切り替えは 1〜2 秒かけて移ります（押した瞬間に空と路面が変わると作り物に見えるため）。

ただし**霧の見え方はカメラによって変えてあります**。視程は「運転席から前を見た距離」なので、
300m 上空の俯瞰にそのまま適用すると街が 1 つも見えない真っ暗な画になってしまいます。

| カメラ | 濃霧（視程 18m）での見え方 |
|---|---|
| 運転席・追従 | **視程どおり。** 24m 先から先は霧に沈んで見えない |
| 俯瞰 | 遠くが霞む程度（619m 先まで見える）。街の形は分かる |

天候を入れても**晴れのときの描画コストは変わりません**（銀座・8 台での実測）。

| 天候 | 擬似カメラ描画（8 枚）| 視程 |
|---|---|---|
| 晴れ | 9.7 ms | 120 m |
| 雨 | 13.0 ms | 120 m |
| 霧 | 14.5 ms | 37 m |
| 濃霧 | 15.3 ms | 18 m |

霧のときだけ画素ごとの奥行きが要るので、その分だけ重くなります。

### 認識器

| 項目 | 内容 |
|---|---|
| フレームワーク | Keras 3（**torch バックエンド。TensorFlow は入れていません**）|
| 入力 | 192×144 の擬似カメラ画像（運転席視点、視野角 68 度）|
| 出力 | 6×8 グリッド × 24ch（物体信頼度 1・BBox 4・クラス 6・灯色 3・規制速度 8・距離 1・横偏差 1）と、走行可能領域 9 方向。**出典は `percep/detector.py` の `CHANNELS`** |
| 規模 | 約 153,000 パラメータ |
| 距離の推定 | 既知の寸法（車幅・標識の直径）とボックスの大きさから求める単眼測距 |

擬似カメラはバックエンド側で numpy の透視投影ラスタライズによって描いています
（依存を増やさないため。認識に必要な情報が写っていればよく、陰影や質感は要りません）。

### 認識器を学習する（「モデル作成」タブ）

**取得直後は認識器がまだありません。** その間はシミュレーターの真値から作った
「理想の検出結果」で代用して走ります（何も検出できない状態で走らせても学習が
進まないため）。教師データもこれと同じ経路で作るので、次の順序で立ち上げます。

操作パネルの**「モデル作成」タブ**で完結します。コマンドを開く必要はありません。

1. 「マップ」タブでエリアを読み込む（読み込み済みならそのまま使われます）
2. 「モデル作成」タブで**集める枚数・エポック数・バッチサイズ・モデルの大きさ**を決める
3. 「収集して学習を開始」を押す

| 設定 | 意味 | 既定 |
|---|---|---|
| 何をするか | 収集して学習 / 収集だけ / 学習だけ（保存済みの教師データを使う）| 収集して学習 |
| 教師データを集めるエリア | **読み込み済みのエリアなら待ち時間なし。** 別のエリアは先に OSM から取得します | 読み込み中のマップ |
| 集める枚数 | 200〜4,800 枚。多いほど良いが収集に時間がかかります（4,800 枚で 600 ステップ。画像は uint8 のままなので約 380MB）| 2,400 枚 |
| 乱数種 | 0〜999,999。**同じ種なら何度回しても同じ画**が集まります。クラス内訳が偏っていたら種を変えて集め直します | 0 |
| 天候を混ぜて集める | 晴れだけでなく小雨・雨・霧・濃霧の画も入れます（後述）| オン |
| 弱点を狙って集める | 集める前に**いまの認識器を採点**し、成績の低いクラスと天候を多めに集めます | オン |
| エポック数 | 1〜60 | 12 |
| バッチサイズ | 8〜128 | 32 |
| モデルの大きさ | チャンネル倍率 0.25〜2.0。推論が重ければ下げる | 1.00 倍 |

### 弱点を狙って集める（アクティブラーニング）

「収集して学習」を押すと、集め始める前に**現行の `detector.keras` を 400 枚で採点**します
（銀座で 4〜5 秒）。真値と CNN の検出を突き合わせ、クラス別・天候別の成績を出し、
**成績が低いところほど多く集める**という形で次の収集へ返します。

| 成績 | 収集で何が変わるか |
|---|---|
| 信号機が低い | 信号のある交差点の**手前 18〜55m に、信号へ正対する向きで**車両を置く |
| 速度標識が低い | 標識の手前に同じように置く |
| 車両が低い | 車両どうしをより密に寄せる（半径 45m → 22m）|
| 障害物が低い | パイロンを 1 台あたり 1 個 → 3 個、より近くに置く |
| 霧が低い | 霧・濃霧の枚数を増やす |

結果は画面の「収集前に測った弱点」に出ます。**これは学習後ではなく、収集を始める前の
成績です。** 認識器がまだ 1 つも無い初回は、採点する相手がいないので一様に集めます。

**なぜ要るのか。** 晴れだけで学習した認識器は、雨ではほとんど無傷なのに霧で崩れます。
外から見ていても気づけないので、機械的に測って集め直す仕組みにしてあります。
銀座・2,400 枚・12 エポック・同一シードでの実測:

| 集め方 | 晴れ | 雨 | 霧 | 全体 |
|---|---|---|---|---|
| 晴れのみ・一様 | **79.4%** | 78.8% | **11.5%** | 59.6% |
| 天候を混ぜる・弱点を狙う | 65.1% | 70.2% | **71.3%** | **68.7%** |

霧が 11.5% → 71.3% になる代わりに、晴れが 79.4% → 65.1% へ落ちます。晴れの教師データが
2,400 枚から 352 枚（14.7%）に減るためで、**枚数を増やさずに天候を増やせば 1 天候あたりは
必ず薄くなります。** 天候を混ぜるなら枚数も増やしてください。

> **狙いの強さは `percep/evaluate.py` の `FOCUS_GAIN`（1.5）が唯一の出典です。**
> 3.0 で試したときは霧 65.4% / 晴れ 63.0% / 全体 63.6% で、**弱点を狙いすぎて
> できていたことを忘れました**。上げるときはこの表を測り直してください。

進捗・損失の推移・集めた教師データのクラス内訳がその場に出ます。完了すると
`backend/data/detector/detector.keras` が作られ、**サーバーを再起動しなくても
その場で載せ替わります**（「いまの認識器」の「観測の出どころ」が
「真値フォールバック」から「CNN の認識結果」に変わります）。

> **実行中は走行も強化学習も止まります。** 収集も学習も CPU を使い切るためで、
> 完了・中断すると自動で再開します。止まるのは物理と PPO だけで、画面と操作は生きています。
> **実行中はエリアも変えられません**（教師データはいま走っているエリアで集めているので、
> 途中で変えると「収集は元のエリア・画面は新しいエリア」という食い違いが起きます）。
> 「中止」を押してもすぐには止まりません（処理中のバッチの切れ目まで進みます）。
> **中断したモデルは保存しない**ので、それまでの認識器はそのまま残ります。

**収集後に出るクラスの内訳を必ず確認してください。** 件数が 0 のクラスは学習しても
検出できるようになりません（車両とパイロンを写すため、収集中は車両を寄せ集めて
前方にパイロンを置いています）。0 件のクラスがあれば画面にも警告が出ます。

### コマンドから学習する

同じ学習は CLI からも実行できます。**中身は同じ実装**（`app/percep/trainer.py`）
なので、どちらから回しても出来上がるモデルは同じです。

```powershell
cd "C:\Users\<ユーザー名>\Documents\GitHub\DriveRL\backend"
.venv\Scripts\python.exe train_detector.py --preset ginza --samples 2400 --seed 0 `
    --epochs 12 --batch-size 32 --width 1.0
```

- `--collect-only` で教師データの収集だけ、`--train-only` で学習だけを行えます
  （**同時には指定できません**）
- `--no-weather` で晴れの画だけを集め、`--no-focus` で収集前の採点をとばします
  （どちらも既定は有効。画面の 2 つのスイッチと同じもの）
- 値域は画面のスライダーと同じで、外れた値は理由を出して終了コード 2 で止まります
- 教師データ（`data/detector/dataset/detector_dataset.npz`）には**形式の版番号**が
  入っています。カメラ解像度や検出クラスを変えた後の古いデータは
  「収集し直してください」と断られます（黙って学習が通って、何も検出しない
  モデルができあがるのを防ぐため）
- **CLI から回すときはサーバーを止めておいてください**（どちらも CPU を使い切ります）。
  画面から回す場合はサーバーが自分でシミュレーションを止めるので、その必要はありません
- 学習が終わると、次回サーバーを起動したときに自動で読み込まれます

### 何を認識しているのかを見る

「表示」タブでカメラを**運転席**にすると、認識したものにバウンディングボックスと
名称が重なります。

| 表示 | 意味 |
|---|---|
| 信号機：青 / 黄 / 赤 | 検出した灯器と、読み取った灯色（バウンディングボックス）|
| 速度標識：40km/h | 検出した規制標識と、読み取った規制速度（バウンディングボックス）|
| 車両 / 障害物 | 検出した前方車両・パイロン（バウンディングボックス）|
| 走行車線 | **路面に重ねた帯**（ボックスではありません）|

ボックスの脇に出る数値は推定距離です。**ここに出ているものが、そのまま強化学習の
入力になっています。** 画面用に描き直してはいないので、認識が外れていれば
そのとおりに外れて見えます。

**車線だけはボックスではなく路面へ直接描きます。** 車線は細長い曲線なので、矩形で
囲んでも正確に認識できているかが分かりません。**実際の白線の上に重ねてある**ので、
認識がずれていればそのままずれて見えます。路面に描いているため、この表示だけは
俯瞰・追従カメラでも出ます。

なお**認識器が返す車線は直線です**（CNN は横のずれと向きまでしか出さず、曲率を
持たないため）。認識器を学習する前の真値フォールバックでは道なりの曲線が描かれるので、
差し替えると車線の描画が直線的になります。これは表示の都合ではなく、
認識器が持っている情報がそこまでだということです。

ボックスは運転席カメラでのみ表示します（擬似カメラは運転席の視点で描いているので、
別の視点に重ねても対象物の上に乗らないためです）。「表示」タブのスイッチで
まとめて出し入れできます。

### 性能への影響

**画像認識ベースにした代償として、車両数は 8 台が上限です**（以前は 64 台）。
1 ステップごとに車両ぶんの描画と推論が走るためです。銀座での実測:

| 内訳 | 時間 |
|---|---|
| 擬似カメラ描画（8 枚） | 12.88 ms |
| CNN 推論（8 枚バッチ） | 28.81 ms |
| **1 ステップ全体（認識器あり）** | **32.04 ms** → 実効 1.56 倍まで |
| 1 ステップ全体（認識器の学習前） | 10.05 ms → 実効 4.98 倍まで |

歩行者を 64 人出すと、真値で走らせたときの 1 ステップが銀座で 13.6ms → 17.9ms、
金沢で 19.6ms → 23.5ms に増えます（いずれも予算 50ms 内）。
転送量は 64 人で 5,871B/frame ＝ 20Hz なら 114.7KB/s 増えます。

倍速スライダーは 8 倍まで動きますが、**認識器を使うと 1.5 倍前後で頭打ち**になります。
HUD の「実効 N 倍」に実測値が出ます。速すぎて追いつかない場合は車両数を減らしてください。

## 走行のルール（日本の道路交通法）

車両は道路中心線ではなく**車線に沿って**走ります。経路そのものが車線に沿って作られるので、
走行側（強化学習）は経路を追うだけでよく、車線判断のロジックを持ちません。

| ルール | 根拠 | 実装 |
|---|---|---|
| 左側通行 | 17 条 4 項 | 対面通行路では中心線の左半分の車線だけを使う |
| 一番左の車線を走る | 20 条 1 項 | 既定で最も左の車線を通る |
| 左折時は左側端に寄る | 34 条 1 項 | 左折・直進の手前は左端車線のまま |
| 右折時は中央に寄る | 34 条 2 項 | 右折の 35m 手前から自分の方向の最も右の車線へ滑らかに移る |
| 赤信号で停止線を越えない | 施行令 2 条 | **停止線の手前で必ず止まる**。越えると罰（既定 -60）|
| 最高速度を超えない | 22 条 1 項 | 道路ごとの規制速度（最高速度標識）を**超えない**。超えると罰（既定 -5）|

交差点では前後の車線中心線がつながらないため、両端を切り詰めてベジエ曲線でつなぎます。
これが右左折の軌跡です。車線変更は「経路の横方向オフセットを手前で滑らかに変える」ことで
表現しているので、交差点で急に車線をまたぐことはありません。

### 信号に対する操作

灯色ごとに、次のステップの速度に上限を掛けています。

| 灯色 | 与える操作 |
|---|---|
| **青** | 制限なし |
| **赤** | 停止線の手前で止まりきれる速度まで抑える |
| **黄** | 安全に止まれるなら赤と同じ。止まれないなら制限なし（施行令 2 条ただし書き）|

エージェントの指令を書き換えるのではなく**環境の性質**として扱うので、
強化学習から見れば「赤信号に近づくとアクセルが効かなくなる環境」でしかなく、学習は成立します。

「シミュレーション」タブの **信号に従う** で切れます。切ると赤信号を越えた罰だけが残り、
守れるようになるかは学習しだいになります。

実測（全開加速し続けるという極端な行動を 9.6 万車両ステップ与えた場合）:

| | 信号順守なし | **信号順守あり** |
|---|---|---|
| 赤信号無視 | 141 回 | **7 回** |
| 赤信号直前で停止していた割合 | 5.4% | **93.3%** |
| 赤信号直前の平均速度 | 11.05 m/s | **0.24 m/s** |
| 青信号直前の平均速度 | — | 5.44 m/s（止まらず進む）|

学習した方策で走らせた場合は **78 エピソードで 0 回**でした。

学習の進み具合は「学習」タブの次の 2 つで確認できます。

| 指標 | 見かた |
|---|---|
| 信号無視/エピソード | 1 エピソードあたり何回赤信号で停止線を越えたか。0 に近づけば守れている |
| 車線逸脱（平均）| 走るべき車線の中心から横に何メートルずれているか。市街地の車線幅はおおむね 3m なので、**1.5m を超えると隣の車線や対向車線にはみ出している**。0.5m 以下なら車線をよく保てている |

### 最高速度標識に対する操作

道路ごとの規制速度は OSM の `maxspeed` から取っています。タグが無い道路は `highway` 種別の
既定値（`residential` なら 30km/h）で埋めます。銀座では **30km/h が 175 本 / 50km/h が 86 本 /
40km/h が 31 本 / 20km/h が 1 本**と実際にばらついています。

標識は **規制速度が変わる進入口にだけ**立てます。同じ速度が続く直線に同じ数字を並べても
情報が増えないためで、規制が変わる地点に設置するという実際の運用にも合います。

| プリセット | 最高速度標識 | （参考）信号灯器 | 標識の規制速度の内訳 [km/h] |
|---|---|---|---|
| 銀座 | 136 基 | 261 基 | 20:1 / 30:59 / 40:22 / 50:54 |
| 梅田 | 54 基 | 73 基 | 30:10 / 40:29 / 50:15 |
| 栄 | 91 基 | 151 基 | 30:38 / 40:32 / 50:21 |
| 金沢 | 15,719 基 | 2,736 基 | 20:4 / 30:6,954 / 40:6,327 / 50:2,248 / 60:178 / 80:8 |

金沢は市街地全域なので桁が違います。道路 58,120 本のうち **30km/h が 48,012 本（83%）** で、
住宅地の生活道路が大半を占めることが数字に出ています。一方で 60km/h が 215 本・**80km/h が
13 本**あり、これは自動車専用道路です（後述の「高架を地上道路として扱う」弱点に該当します）。

信号と同じく**環境の性質**として扱います。経路を張るときに「弧長 → 規制速度」の区切りを
求めておき、毎ステップ現在位置の規制速度を引いて、カーブ・信号と合わせて**最も厳しい上限**を
採ります。指令を書き換えるのではなく、上限を超えないところまで加速指令を丸めるだけです。

「シミュレーション」タブの **標識に従う** で切れます。切ると速度超過の罰だけが残り、
守れるようになるかは学習しだいになります。

実測（銀座・16 台・全開加速し続けた場合）:

| | 標識順守なし | **標識順守あり** |
|---|---|---|
| 規制速度の最大超過 | 20.04 km/h | **0.00 km/h** |
| 規制速度への到達率 | — | 100%（頭打ちが厳しすぎない）|
| 平均速度（信号あり）| 8.68 km/h | 8.65 km/h（**-0.4%**）|
| 平均速度（信号なし）| 32.75 km/h | 28.99 km/h（-11.5%）|

**既定の設定では、標識を守らせてもほとんど遅くなりません。** 全交差点に信号を置いてあるため
時間の 64% を停止して過ごしており、規制速度が上限になる場面がそもそも少ないからです。
標識だけの影響を見たいときは「信号に従う」を切ってください（-11.5%）。

**速度超過は「超え始めた瞬間」を 1 回と数えます。** 毎ステップ数えると、1 度超えただけで
戻るまでの数十ステップぶん罰が積み上がり、報酬がそれに支配されてしまいます。車線逸脱と
同じ考え方で、`+0.5 m/s` を超えたら「超過」、`+0.1 m/s` を下回ったら「復帰」という
ヒステリシスを付けてあります。

> **「学習」タブの速度超過が 0 のままでも異常ではありません。** 標識順守が有効なあいだは
> 環境側が超えさせないので 0 が正常です。指標として見たいときは「標識に従う」を切ってください。

罰を **-5** と信号無視（-60）より軽くしてあるのは、速度超過が事故に直結する度合いで
赤信号無視に劣るためです。同格にすると停止挙動の学習を邪魔します。

> 実装していないこと: 停止車両を追い越すための車線変更、一時停止標識、右折時の対向車優先。

## 信号機・道路標示・道路標識

「表示」タブで出し入れできます。いずれも日本の基準に合わせてあります。

### 信号機

OSM の `highway=traffic_signals` から実際の交差点位置を取り、
接続道路が 3 本以上の交差点に、**進入できる方向の数だけ**設置します。

| 項目 | 実装 |
|---|---|
| 灯器 | 横型 3 灯式。**運転者から見て左から 青・黄・赤**（赤が右端）|
| 設置位置 | 交差点の**対面側**。停止線で止まった運転者が交差点越しに正対して見る配置 |
| 支柱 | 進行方向の**左側**に立て、アームで車道上へ張り出す（左側通行のため）|
| 高さ | 灯器下端が路面から 5.0m。灯火径 300mm、各灯にフード |
| 現示 | 青 25 秒 → 黄 3 秒 → 全赤 2 秒 →（次の現示へ交代）。サイクル 60 秒 |

黄を挟まずに青から赤へ飛ぶことはなく、交代の前に必ず全赤（クリアランス）が入ります。
**交差する流れが同時に青になることはありません。**

現示は交差点ごとに、**軸（向きの正負を無視した方向）のそろった進入路**をまとめて作ります。
十字路なら 2 つですが、**進入路が 3 本以上ある交差点は 3 つ以上**になります
（実測: 金沢の 757 交差点のうち 3 現示が 41・4 現示が 2、梅田は 31 のうち 3 現示が 3）。
**サイクル 60 秒は現示の数で分け合う**ので、青は 3 現示なら 15 秒・4 現示なら 10 秒です。
待たされる赤はいちばん長い交差点で 47.0 秒（銀座は 32.0 秒）。
`backend/verify_signal_phases.py` が、同じ現示に交差する流れ（軸差 30 度以上）が
入っていないかを全プリセットで検査します。

**歩行者用信号**は、車両信号 1 基につき横断歩道の両端へ 1 基ずつ立ちます。

| 項目 | 実装 |
|---|---|
| 灯器 | 縦型 2 灯式。**上が赤・下が青**。灯火径 250mm、高さ 2.55m |
| 設置位置 | 車両信号の停止線の先（横断歩道の両端）。**渡ってくる人に正対** |
| 現示 | **車両信号の裏返し**。車が赤で止まっていれば歩行者は青 |

歩行者はこの信号に従います。**赤のうちは横断を始めず、歩道の手前で待ちます。**
渡っている最中に赤へ変わっても引き返さず、渡り切ります（実際の歩行者と同じ）。
信号の無い交差点では従来どおり自由に渡ります。

実測（銀座・64 人・120 秒）: 横断を始めた 56 回のうち**赤のうちに渡り始めたのは 0 回**、
いちばん長い信号待ちは 27.8 秒（サイクルは 60 秒）でした。

### 道路標示

「道路標識、区画線及び道路標示に関する命令」の寸法に合わせています。

| 標示 | 寸法 | 引く条件 |
|---|---|---|
| 車道中央線 | 幅 15cm・5m 線 / 5m 空白の破線 | 対面通行の道路 |
| 車線境界線 | 幅 15cm・5m 線 / 5m 空白の破線 | 片側 2 車線以上 |
| 車道外側線 | 幅 15cm の実線 | すべての道路の両端 |
| 停止線 | 幅 45cm の実線 | 信号機のある進入路 |
| 横断歩道 | 帯幅 45cm・間隔 45cm・横断方向 4m | 停止線の先。縁線のない現行のゼブラ型 |

**追越し禁止の黄色実線は描いていません。** これは公安委員会の規制であって OSM のタグからは
判別できないためです。判別できないものを描くと「そこは追越し禁止だ」という誤った情報になります。

### 最高速度標識

規制標識「最高速度」を、**規制速度が変わる進入口**に立てます
（銀座 136 基 / 梅田 54 基 / 栄 91 基 / 金沢 15,719 基）。
走行への効き方は「走行のルール」の節を参照してください。

| 項目 | 実装 |
|---|---|
| 標示板 | 白地の円に赤縁・黒数字。直径 60cm |
| 数字 | `speedLimit` を km/h の整数へ丸めた値（8.333 m/s → 30）|
| 設置位置 | 進行方向の**左側**の路端（左側通行）。交差点から 12m 先 |
| 高さ | 標示板の下端が路面から 1.8m（設置基準の下限）|
| 向き | 進入してくる運転者に**正対**する |

**標識の配色は昼夜で変えていません。** 信号の灯火と同じ理由で、現実の標識が環境によって
色を変えないからです。支柱の色だけ配色に追随します。

こちらも OSM の `traffic_sign` ノードではなく道路（way）の `maxspeed` から生成しています。
日本の対象エリアでは `traffic_sign` がほとんど登録されておらず、それだけでは 1 基も
立たないためです。

「表示」タブでカメラを 3 つのモードから選べます。

| モード | 視点 |
|---|---|
| 俯瞰 | 自由視点。ドラッグで回転、ホイールでズーム、右ドラッグで平行移動 |

## 学習したモデルを書き出す

右パネルの「学習」タブ →「モデルの書き出し」から、3 つの形式でダウンロードできます。
書き出しはサーバー側の学習ループの切れ目で行われるので、**学習は止まりません**。

| 形式 | 使いみち |
|---|---|
| 重み一式（`.pt`）| 「読み込み」で戻せば**続きから学習を再開**できる。バックアップ・別マシンへの持ち出し |
| TorchScript（`.torchscript.pt`）| このリポジトリのコード無しで推論できる。他の PyTorch プログラムへの組み込み |
| **Keras（`.keras`）**| 同じネットワークを Keras 3 のモデルとして組み直したもの。Keras / TensorFlow 系のツールで扱う |

いずれにも**観測ベクトルの構成と行動のスケール**がメタデータとして埋め込まれます。
これが無いと、受け取った側は 66 次元の入力に何を入れればよいか分からず、
ファイルは読めても実際には使えません。観測の正規化に使う `vehicle.maxSpeed` は
**定数ではなく実行時に変えられるパラメータ**なので、書き出した時点の値を
メタデータに入れてあります（`steerRate` / `maxLateralAccel` も、舵角を再現するには
`maxSteer` だけでは足りないため同梱しています）。

### 書き出した TorchScript を使う

```python
import json
import torch

extra = {"metadata.json": ""}
policy = torch.jit.load("autoware-sim_ginza_upd585_20260905-163218.torchscript.pt",
                        _extra_files=extra)
meta = json.loads(extra["metadata.json"])

print(meta["observation"]["layout"])   # 66 次元の内訳
print(meta["action"]["fields"])        # accel / steer の物理量への換算

obs = torch.zeros(1, meta["model"]["obsDim"])   # (B, 66) float32
action, value = policy(obs)                     # action: (B, 2), value: (B,)

accel_cmd, steer_cmd = action[0].tolist()
accel = accel_cmd * meta["vehicle"]["maxAccel"] if accel_cmd >= 0 \
    else accel_cmd * abs(meta["vehicle"]["maxDecel"])   # [m/s^2]
steer = steer_cmd * meta["vehicle"]["maxSteer"]         # [rad]
```

`action` は方策分布の平均をクリップした決定論的な行動です。学習時と同じ探索を再現したい場合は、
同梱の buffer `log_std` を使って `Normal(action, exp(log_std))` からサンプリングしてください。
`log_std` は学習時と同じ可動域（`meta["policy"]["logStdRange"]` = -5.0〜0.0）へ
丸めた値が入っており、メタデータの `policy.logStd` とも一致します。

コマンドラインからでも取れます。

```powershell
curl.exe -OJ http://127.0.0.1:8000/api/export/checkpoint
curl.exe -OJ http://127.0.0.1:8000/api/export/torchscript
curl.exe -OJ http://127.0.0.1:8000/api/export/keras
```

### 書き出した .keras を使う

```python
import json, zipfile
import keras   # 環境変数 KERAS_BACKEND=torch で TensorFlow 無しでも動く
import numpy as np

model = keras.saving.load_model("autoware-sim_ginza_upd427_20260905-211557.keras")

# メタデータは .keras（zip）の中に同梱してある
with zipfile.ZipFile("autoware-sim_ginza_upd427_20260905-211557.keras") as z:
    meta = json.loads(z.read("autoware_sim_metadata.json"))
print(meta["observation"]["layout"])        # 66 次元の内訳

obs = np.zeros((1, meta["model"]["obsDim"]), dtype="float32")   # (B, 66) float32
action, value = model.predict(obs)          # action: (B, 2), value: (B,)（TorchScript 版と同じ shape）
print(meta["policy"]["logStd"])             # 探索ノイズを再現したいとき用
```

**`custom_objects` は要りません。** 標準の Dense 層だけで構成し、行動のクリップは
`hard_tanh` 活性で表しています（`clip(x, -1, 1)` と厳密に一致します）。

Keras 3 は PyTorch をバックエンドにできるので、このプロジェクトでは
**TensorFlow を入れていません**。読み込む側も `KERAS_BACKEND=torch` で構いません。

### 書き出したモデルから学習を再開する

「学習」タブ →「モデルの読み込み」で、書き出した**重み一式（.pt）**を選ぶだけです。
重みに加えて Adam のモーメントと更新回数も戻すので、学習が仕切り直しになりません。

- 載せ替える直前に、**それまでのモデルが `backend/data/exports/` へ自動退避されます**
  （`..._before-import_....pt`）。間違ったファイルを選んでも学習成果は失われません。
- 読み込み後すぐに `backend/data/checkpoints/shared_policy.pt` も更新されるので、
  サーバーを再起動しても読み込んだ状態が残ります。
- `backend/data/exports/` は**新しい順に 20 世代まで**しか残しません。書き出すたびに
  古いものが消えるので、残したいファイルは別の場所へ移してください
  （退避直後の `..._before-import_....pt` は、その回の削除対象からは外れます）。
- TorchScript 版と Keras 版は推論専用なので学習の再開には使えません
  （選ぶと「これは Keras 形式（.keras、推論専用）のファイルです」のように表示されます）。
- 観測次元やネットワーク構成を変更した後のモデルは読み込めません。
  その場合は「ファイル: 57 / このアプリ: 66」のように食い違いが表示されます。

> **安全上の注意**: `torch.load` は通常 pickle を実行するため、出所の分からない `.pt` は
> 任意コード実行の入口になり得ます。本アプリは受け取ったファイルを必ず
> `weights_only=True` で解析し、テンソルと素の値以外が入っていれば読み込みを中止します。
> 詳しくは `SECURITY.md` を参照してください。

## 設計上の要点

| 項目 | 方針 |
|---|---|
| 学習方式 | オンライン学習。表示中も重みが更新され続ける |
| エージェント | 最大 8 スロットを事前確保し、未使用は観測・行動をマスク（画像認識のコストで 64 → 8）|
| ポリシー共有 | 全車両が同一の重みを使う。追加した車両も即座に学習成果を使える |
| 認識 | 擬似カメラ 192×144 → CNN（Keras 3 / torch）→ 検出結果。**学習の入力と画面のボックスは同じもの** |
| 天候 | 雨は画だけを濁らせ、霧は視程を縮める。**視程は描画と正解ラベルが共有する 1 つの値** |
| 教師データ | 収集の前に現行の認識器を採点し、**成績の低いクラス・天候を多めに集める**（走行中には一切乗らない）|
| 観測 | 66 次元。**カメラ認識**（車線 4 / 信号 5 / 標識 3 / 前方車両 12 / 障害物 9 / 歩行者 9 / 走行可能領域 9）＋**センサーとナビ**（自車 2 / 目的地 3 / 経路案内 10）。**内訳の出典は `backend/app/config.py` の `OBS_*`** |
| 行動 | 2 次元（加減速・操舵）いずれも [-1, 1] |
| 報酬 | 目的地到達・衝突回避・経路進捗・信号順守・最高速度順守 |
| 物理 | キネマティック自転車モデル。建物衝突は**バックエンドで判定**し、結果をフロントへ送る |
| 一時停止 | **描画だけ**が止まる。裏側の学習は止まらない |
| 認識器の学習 | 「モデル作成」タブから専用スレッドで回す。**その間だけは物理と PPO も止める**（CPU と `groundtruth` の静的キャッシュを取り合わないため）|
| 学習と描画の分離 | サーバー 20Hz / ブラウザ 60fps。フロント側でフレーム間を補間する |
| 永続化 | PPO の重みとオプティマイザ状態を自動保存し、次回起動時に復元 |
| 通信 | WebSocket（状態配信・操作）+ HTTP（モデルの入出力）|

### 実測性能（Intel Core Ultra 7 155H / CPU のみ）

| 項目 | 値 |
|---|---|
| 1 ステップの計算時間（8 台）| **認識器あり 32.04ms** / 認識器の学習前 10.05ms |
| 内訳（8 台）| 擬似カメラ描画 12.88ms + CNN 推論 28.81ms + 物理・PPO |
| 天候による擬似カメラ描画の増分（8 台）| 晴れ 9.7ms → 雨 13.0ms / 霧 14.5ms / 濃霧 15.3ms。**晴れのときは増えない** |
| 収集前の採点（400 枚）| 4〜5 秒。**収集のときだけ走り、走行中のステップには乗らない** |
| 出せる最大倍速（実測）| 認識器あり **1.56 倍** / 学習前 4.98 倍 |
| 参考: ground truth 観測だった頃 | 8 台 7.03ms / 32 台 9.68ms / 64 台 13.22ms（3.8 倍）|
| PPO 更新 | 勾配更新を 1 ステップ 1 回ずつに分割。まとめて回すと 64 台で約 350ms 止まる |
| フレーム配信 | 最大 60Hz（`config.FRAME_HZ`）。物理の刻みとは切り離してある。経路が変わったフレームだけ経路を載せる |
| マップ読込 | キャッシュから 0.3 秒（初回は Overpass API から 30〜150 秒）|
| 配車の経路探索 | 銀座 2.0ms / 金沢 18.8ms（1 ステップの予算は 50ms）。呼んだときだけ 1 回走る |
| 乗降地点での停車精度 | 乗車 0.05m / 降車 0.12m（銀座）。赤信号と同じ速度上限で止めている |
| 歩行者の当たり判定 | 建物の格子索引を作るのに 銀座 4.3ms / 金沢 67.4ms（マップ読込時に 1 回）。1 フレームの判定は 0.6〜1.3μs |

詳細な設計の経緯は `memo/memo_x.x/`（git 管理外。`memo_1.0.md` が初版、
`memo_2.0.md` が実用モードの要件）を参照してください。

```powershell
cd backend; .venv\Scripts\python.exe verify_log_std.py        # 方策分布（log_std）
cd backend; .venv\Scripts\python.exe verify_signal_phases.py  # 信号の現示（プリセット名を渡せば 1 つだけ）
cd backend; .venv\Scripts\python.exe verify_publish_routes.py # 配車と frame の経路が配信で落ちないか
```

`npm run verify` は Node で直接実行する検証スクリプトです。3D の向きは**間違っていても
型チェックもビルドも通ってしまう**ため、幾何計算を React から切り離した純粋モジュールに置き、
数値で不変条件を確かめています。

- 信号機: 灯器が運転者に正対しているか、青が運転者から見て左か、灯器の高さ
- 最高速度標識: 板が運転者に正対しているか（裏を向いていないか）、取り付け高さ
- カメラ: 運転席が右ハンドルの位置にあるか、視線が進行方向を向いているか
- 進路矢印: リボン幅が保たれるか、矢羽根が進行方向を指しているか
- 車両の色: 64 色が CIELAB 距離で十分に離れているか（小さな色見本やピンで見分けられるか）
- 車両の行列: 車体・ノーズ・キャビンの取り付け位置、前輪だけに効く舵角、車輪の転がり
- 日の出・日の入り: 東京の夏至・冬至・春分の昼の長さ、経度による日の出のずれ、
  昼夜の判定と次に切り替わる時刻、白夜・極夜
- 認識結果オーバーレイ: 擬似カメラ（水平 68 度・4:3 固定）と three のカメラ
  （垂直 68 度・可変比）の画角の違いを吸収できているか。ここがずれると
  ボックスが対象物の上に乗らず、「何を認識しているか見せる」目的が果たせない
- 道路標示: 破線の割り付け。**引かれないという形で壊れる**ため
  （画面では「その道路には中央線が無い」としか見えない）
- 配車の自動操作: 段階を飛ばさないか（迎車の途中で乗らない・降りる前に呼ばない）、
  断られたときに 60fps で送り続けないか。**指令を出す順番だけは画面を見ても
  分からない**ので数値で確かめる
- 信号の現示: 同じ現示に交差する流れ（軸差 30 度以上）が入っていないか、群が 0 から
  連番か、赤で待たされるのが 60 秒未満か。**同時に青になっても双方の車が止まらないだけ**なので、
  画面では「たまたま出会わなければ」見えず、衝突率だけが底上げされる
- コメント規約と CSS: コード中に `★` が残っていないか、docstring と `/** */` が
  1 行に収まっているか、`transition` にレイアウトを起こすプロパティが乗っていないか。
  **どれも型チェックもビルドも通ってしまう**ので、宣言だけでは守られない
  （実際に `★` は 133 件まで増え直した）
- 天候: フォグの距離が霧の濃さに対して単調に縮むか、視点が高いほど緩むか
  （**俯瞰で街が完全に消えないこと**）、雨が視程を縮めないこと、明るさの下限、
  天候の移り変わり（雨がやんだ直後は空が先に晴れ、路面はまだ濡れていること）
- 徒歩キャラクター: 体の寸法（足が接地しているか・目線が頭より下か）、手足の振りが
  左右逆位相か、支点で回した世界行列がシーングラフと一致するか、建物の当たり判定、
  **壁沿いに滑れること**（軸ごとに判定しないと、壁に触れた瞬間に動けなくなる）、
  照準が背後の車両を拾わないこと、降車位置が車体の左（歩道側）に出ること
- スマホ画面の 2D 地図: 倍率 1 でマップ全体が収まるか、投影と逆投影が一致するか
  （**地点を選ぶのに使うので、ここがずれると違う場所へ配車される**）、
  北が上か、ホイールで拡大したとき掴んだ点が画面上で動かないか、
  配車に合わせた自動ズームが 2 点を余白つきで収めるか、倍率の補間が対数か、
  **乗車中に地図を回したときも投影と逆投影が往復するか**、進行方向が画面の真上に来るか、
  回しながらレイヤを貼り替えても地物が同じ画素に乗るか、向きの補間が近いほうへ回るか
  （線形だと寄り方が跳ねる）、**別の倍率で描いた地図レイヤを貼り替えても
  地物が同じ画素に乗るか**（寄っている最中に道路を引き直さないための仕組み）

実際にこの仕組みが、灯火の並びが左右逆（左から赤・黄・青）になっていたバグを検出しました。

車両の行列は、描画を InstancedMesh へ変えた際に three のシーングラフから自前計算へ
移したものです。**移す前の親子構成を検証スクリプト側で組み直し、世界行列を要素ごとに
突き合わせて**います（車体の最大差 0.0、車輪 2.2e-16）。

## つまずきやすい点

**マップの読み込みが終わらない / 失敗する**
Overpass API の混雑が原因のことが多いです。`backend/data/osmnx_cache/` にキャッシュが残るので、
時間をおいて `python -m app.map.prefetch` を再実行してください。

**本当に学習しているのか分からない**
「学習」タブの一番上に**ネットワークのノード図**があります。

- 左上の点が脈打っていれば、重みが更新されています
- 表の **勾配** が 0 でなければ、逆伝播が流れています
- 表の **Δ（直前の更新）** が 0 でなければ、重みが実際に動いています

**全車両はこの 1 つのネットワークを共有しています**（parameter sharing）。
車両ごとに別々の学習はしていません。台数を増やすのは学習者を増やすためではなく、
経験を集める速度を上げるためです。

**隠れ層の構成を変えたい**
同じカードの一番下で、層の数（1〜4）と各層の幅（32〜256）を選べます。
**重みは引き継げないので学習は 0 からやり直し**になります。残したい場合は
先に「モデルの書き出し」で保存してください。深くするほど 1 ステップの計算時間が
伸びて実効倍速が落ちるので、まず今の構成で学習が進むか見てから変えるのが確実です。

**いつまで経っても学習が進まない / 動きがランダムに見える**
「学習」タブの**エントロピー**を見てください。行動は 2 次元なので、
探索の広さが健全なら **1.8 前後**です。**4.8 近くまで上がっていたら、
探索ノイズが行動範囲より広くなっており、方策が実質ランダムに潰れています**
（過去にこの状態で 8,925 回ぶん学習が無駄になりました）。
その場合は「ポリシーを初期化」でやり直してください。
`backend/verify_log_std.py` で分布側の健全性を検査できます。

**1.8 は初期値（探索ノイズ 0.6）に対応する数字で、下がること自体は異常ではありません。**
学習が進めば探索は狭まります。警戒すべきは上がりすぎる側です。
なお `warmstart_policy.py` で立て直した直後は探索ノイズを 0.3 に揃えるので、
エントロピーは **+0.4 前後**になります。この値は `log_std` だけで決まるため、
ほとんど動かないように見えても異常ではありません。**学習が進んでいるかは
エントロピーではなく、勾配・Δ・到達率で見てください。**

**どの車両も止まったまま、まったく動かない**
方策が「止まる」に固まっています。学習が進むほど悪化し、信号でも規制速度でもなく
**アクセル指令そのものが常にフルブレーキ**（-1 付近）になります。

まず `backend/warmstart_policy.py` で回復させてください。
**サーバーは止めてから**実行します（動かしたままだと自動保存と取り合いになります）。

```powershell
cd backend
.venv\Scripts\python.exe warmstart_policy.py --preset ginza
```

実用モードのタクシーを走らせている経路追従の操作を教師にして、**方策・価値関数・探索の幅**を
まとめて立て直します（行動クローニング）。数分で終わり、そのまま PPO の学習を続けられます。
実測では **60 秒での移動が 0〜3m から 113〜488m** になり、止まったままの台数は 5/8 → 0/8、
その後 18 更新ぶん学習を続けても走り続けました。
元の重みは `data/checkpoints/shared_policy.pt.before-warmstart` に残ります。

**実行中はサーバーを止めたままにしてください。** 動かしたまま直しても、サーバーが学習を
数更新進めた時点で壊れた重みを書き戻します（実際にそうなりました）。

原因そのものは**修正済み**です。行動の平均に範囲の制約が無かったため、
環境側の `clip(-1, 1)` では区別できない範囲外（実測 -1.710）へ平均が流れ出し、
**アクセルを正にする選択肢が構造的に消えていました**（80.2% の状況で、
探索ノイズを 3σ 足しても正に届かない）。いまは平均を `tanh` で範囲内に収めています。

**なお、方策だけを立て直すのでは足りません。** 「止まる前提」で学習し切った価値関数を
残したまま走り出すと、予測と実測の食い違いがそのまま advantage の誤差になり、
**2 更新で元に戻ります**（実測）。`warmstart_policy.py` は価値関数と探索の幅も
セットで直すので、そのまま使えば大丈夫です。

**車両の動きがぎこちない・信号を無視する**
学習初期は正常です。オンライン学習なので、最初は壁にぶつかったり赤信号で突っ込んだりします。
「学習」タブの到達率と信号無視の推移で進み具合を確認してください。

**`5173 is in use` と出て Vite が起動しない**
前回の Vite が残っています。`run.ps1` / `run.cmd` は Ctrl+C で node まで落としますが、
ターミナルごと閉じるなど強制的に終了させると残ることがあります。
`Get-Process node` で確認し、`Stop-Process -Id <PID>` で片付けてください。

**道路が高速で点滅する / 路面と地面がちらつく**
深度バッファの精度不足（Z ファイティング）です。**修正済み**ですが、もし再発したら
`RoadNetwork.tsx` と `RoadMarkings.tsx` の `polygonOffset` を確認してください。
地面 < 路面 < 中央線 < 白線標示 の順に手前へ押してあります。

**フレームレートが出ない**
「表示」タブでまず影を切ってください。建物は数千件をマージして 1 メッシュで描いていますが、
影の計算はそれとは別に効いてきます。道路標示・信号機も切れます。

**学習をやり直したい**
「学習」タブの「ポリシーを初期化」を使ってください。実行前に確認が入ります。

**以前書き出したモデルが読み込めない**
観測ベクトルの次元が変わると、それ以前のモデルは読み込めません
（「ファイル: 57 / このアプリ: 66」のように食い違いが表示されます）。これまでの変更:

| 変更 | 観測次元 |
|---|---|
| 信号を観測に加えた | 50 → 54 |
| 最高速度標識を観測に加えた | 54 → 56 |
| **画像認識ベースへ移行した** | **56 → 57**（値の意味も真値から認識結果へ変わりました）|
| **歩行者を観測に加えた** | **57 → 66**（歩行者 3 人 × 前後・左右・信頼度）|

**バウンディングボックスが出ない**
カメラが「運転席」になっているか確認してください（追従・俯瞰では出しません）。
「表示」タブのスイッチでも出し入れできます。それでも出ない場合は、車両一覧から
車両を選んで追跡対象にしてください。

**認識器を学習したのに何も検出しない**
収集後に出る**クラスの内訳**を確認してください（「モデル作成」タブにも CLI にも出ます）。
件数が 0 のクラスは検出できるようになりません。集める枚数とエポック数を増やすのも
有効です。学習の最後に**検証時の検出数**が出るので、そこが 0 なら学習が足りていません
（「モデル作成」タブでは警告としても出ます）。

**「モデル作成」タブで学習を始めたら車が止まった**
そういう仕様です。収集も学習も CPU を使い切るため、完了・中断まで物理と PPO を止めます。
「シミュレーション」タブと「学習」タブにも止まっている旨が出ます。自動で再開するので、
待つか「学習を中止」を押してください。

**認識器を入れたら遅くなった**
そういう仕組みです（1 ステップ 10ms → 32ms）。車両数を減らすか、
「モデル作成」タブの**モデルの大きさ**を 0.5 倍にして学習し直してください
（CLI なら `--width 0.5`）。
