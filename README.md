# DriveRL

現実の道路マップ（OpenStreetMap）上で、**マルチエージェント強化学習（自作 PPO）で走る自動運転車**を
リアルタイムに学習させながら、3D で眺めたり介入したりできるシミュレーターです。

- **学習は表示中も裏で進み続けます。** 画面に映っているのは再生ではなく、いま重みが更新されている方策の挙動です
- **車両は擬似カメラの画像を CNN で認識した結果だけを見て走ります。** 信号の灯色も標識の数字も車線も前の車も、
  画像から検出したものです。認識を誤れば赤信号へ突っ込みますが、衝突や信号無視の判定はシミュレーターが
  真値で行うので、見逃されることはありません
- **バックエンド**（Python / FastAPI）が地図の変換・擬似カメラ・認識・物理・学習を、
  **フロントエンド**（React / TypeScript / Three.js）が 3D の描画と介入を受け持ちます

### 学習・認識パイプラインの分離評価（#102）

`backend/benchmark_pipeline.py` で、学習速度、認識器、運転方策を同じ条件で比較できます。
サーバーや画面は起動せず、学習中の重みはメモリ内だけで更新し、本番の重みを保存しません。
`backend/` から実行します。`grid` は合成地図、実地図は現行キャッシュが必要です。古いキャッシュを自動で再取得しません。

```powershell
# 銀座・金沢の統一比較。実地図のキャッシュは先に app.map.prefetch で更新する
.venv\Scripts\python.exe benchmark_pipeline.py --presets ginza kanazawa --vehicles 1 4 8 --weather clear rain fog --output data/evaluations/pipeline.json

# 外部通信のない短い学習速度確認。CNN や学習済み方策を用意する前でも使える
.venv\Scripts\python.exe benchmark_pipeline.py --tasks speed --modes oracle --presets grid --vehicles 1 4 8 --weather clear --steps 256 --output data/evaluations/speed.json

# 認識器の出力が方策へ与える影響を、同じ重みと乱数種で比較する
.venv\Scripts\python.exe benchmark_pipeline.py --tasks policy --presets ginza --vehicles 8 --weather clear fog --seeds 0 1 --policy-steps 4000 --evaluate-unconstrained --output data/evaluations/driving.json

# 外部 RGB データだけを採点する（地図・運転方策は読み込まない）
.venv\Scripts\python.exe benchmark_pipeline.py --tasks images --external-only --external data/external/manifest.json --output data/evaluations/external.json
```

- 速度は方策・物理・擬似カメラ・CNN・PPO 更新の内訳、中央値/p95/p99、50ms 超過率、秒あたりのステップを記録します。
  既定は画面向け配信データの作成も省きます。`--publish-frame` でその作成時間も含められますが、ブラウザの描画は測りません。
  CNN の観測用画像は常に作ります。`--device keras` / `cpu` / `auto` で既存の推論先を比較できます。
  `--inference-only` は学習更新を省きます。台数の上限は `backend/app/config.py` の `MAX_VEHICLES` です。
- 方策は `oracle`（正解認識）・`cnn`（画像認識）・`noisy`（正解検出の欠落/距離/灯色に雑音）を同じ撮影予算で比較します。
  方策評価では学習と介入を止め、再スポーンの処理時間に状態列が左右されないようにします。速度計測は通常の再スポーン予算を使い、
  `--deterministic-respawn` 指定時だけ外します。CNN の読み込みや推論の失敗時は採点を中止します。
- 到達・衝突・逸脱・信号違反の率は終了したエピソードが分母で、終了ゼロ件は `null`。
  平均到達時間と全終了理由の平均時間を分け、未完了分を含む違反件数と車両時間も記録します。
  既定では真値の信号・規制速度制限が有効です。`--evaluate-unconstrained` は方策評価だけこの制限を外します。
- 認識器は天候と、明るさ・雑音・解像度・中心画角の変更ごとに precision/recall、誤検出の割合、灯色/規制速度の正解率、
  走行可能距離の誤差を出します。画角変更は中心切り抜きによる近似で、箱の教師を合わせ、走行可能距離の教師は除きます。
  出力にはモデル・地図・画像と教師の指紋も入り、どの認識器と方策を比較したか追跡できます。

外部画像は RGB の `uint8` 配列を `.npy` で保存し、同じディレクトリ内の manifest に並べます。
PNG/JPEG のデコードや新しい画像ライブラリは追加していません。画像は認識器の入力寸法へ合わせます。
箱は画像全体を 0〜1 とする座標、灯色は 0=青/1=黄/2=赤、距離・規制速度は m・m/s です。

```json
{"samples":[{"image":"frame.npy","condition":"rain","detections":[{"cls":"TRAFFIC_LIGHT","box":[0.4,0.2,0.5,0.3],"phase":2}]}]}
```

画像をまとめた NPZ も使えます。`images` は `(N,H,W,3)` の uint8、任意の `labels` は各画像の detections 配列を
JSON にした Unicode 配列です。任意の `freespace` は `(N,OBS_FREESPACE_DIM)` の距離で、次元の出典は `config.py`。
object 配列や pickle は読みません。教師省略/null は精度未評価、`[]` は物体が無いという正解です。
外部画像で測るのは認識器の性能で、運転成績はシミュレータ内の結果です。実環境での運転性能を示すものではありません。

### 交通・車両物理のシナリオ（#101）

**通常起動で詳細物理と交通シナリオが常に動きます。** 追加のコマンドや `.env` の指定は不要です。
摩擦・タイヤの横滑り・前後の荷重移動・アクセル／ブレーキ／操舵の応答遅れを持つ詳細物理に、
時間帯別の背景交通と需要応答信号を組み合わせます。標準設定の出典は `backend/app/sim/scenario.py` の
`standard_scenario()` です。学習車と背景車の枠・時間帯ごとの台数もそこで管理し、フロントから変更できません。
最大台数は `backend/app/config.py` の `MAX_VEHICLES` に合わせ、学習車と背景車を合わせて上限まで使います。
開発・実用モード、地図の切り替え、エピソードのリセット後も有効です。
学習・認識パイプラインの高速化も通常運転に組み込まれています。比較評価は同じ条件での独立した試走で、実行例は下記です。

`backend/scenarios/` の JSON は比較評価用の設定例です。`baseline.json` と `wet-road.json` は同じ背景交通で物理を比べ、
`rush-hour.json` は時間帯による増減と需要応答信号、`grid-roadworks.json` は合成マップの道路イベントを試します。

- 学習車と背景車の合計は `config.MAX_VEHICLES` 以内。背景車は個別の速度・時間車間・加減速特性で経路追従し、
  PPO の損失と画面のエピソード成績から除外します。比較評価の台数は JSON で指定します。
  学習車の観測は従来どおりカメラ由来です。背景車と信号制御の内部判断には真値を使います。
- `road_weights` は道路 ID ごとの背景車の出現位置の重み。`events` は道路 ID・開始秒・継続秒を指定した
  `parked` / `construction` / `closure`。既存の障害物で表現するため、カメラ・教師ラベル・衝突判定に同時に反映されます。
  道路 ID は地図ごとに異なり、工事と通行規制は物理的な障害物です。経路網から道路を除去する機能ではありません。
- 信号は時間帯・需要に応じて青の配分を変え、黄・全赤・最短青を保ちます。灯器の `source` は
  OSM タグ由来／補完／不明を区別します。実際の信号周期を取得するものではありません。

同じチェックポイントを複数条件で評価するには、`backend/` から実行します。実マップは先に
`python -m app.map.prefetch` で現行キャッシュへ更新してください。`grid` は外部通信なしで使えます。

```powershell
.venv\Scripts\python.exe evaluate_scenarios.py --scenarios scenarios/baseline.json scenarios/wet-road.json --presets grid --weather clear rain --seeds 0 1 --maneuvers --output data/evaluations/compare.json
```

`--train-steps 8192` を加えると、条件ごとに同じ初期重みへ戻して学習してから比較します。
本番の重みは書き換えず、比較中の学習重みも保存しません。到達率・衝突率・車線逸脱率・信号違反率は
**完了した学習車のエピソード**が分母で、未完了なら `null`。平均速度は停止中を含む車両ステップ平均です。
信号・速度の真値による既存の制約は有効で、CNN の有効状態もレポートに記録します。
`--maneuvers` は 20m/s からの急制動と急操舵を比較します。

詳細物理は車両の実測で同定していません。空力・サスペンション・左右輪の荷重移動は含まず、
低速と後退もスリップの分母を正則化した動的モデルです。横滑り中は車体方向の速度と移動方向が異なり、
比較評価の平均速度には横速度も含めます。リアルタイムの予算と実測値は `CLAUDE.md` の該当節を参照してください。

## 自動運転タクシーに乗る（実用モード）

パネル右上のトグルで**開発モード**（学習を回す）と**実用モード**を切り替えます。実用モードでは重みの更新が止まり、
パネルがスマホ画面に、3D が歩行者の一人称視点に変わります。

1. スマホの **タクシーを呼ぶ** を押し、地図をタップして行き先を選ぶ。**乗車地点はいま立っている場所**です
   （行き先は最寄りの交差点へ寄せられます）
2. **ここまで呼ぶ** で、いちばん近い車が迎えに来ます。事故や道の詰まりで来られなくなったら、配車はそのままで
   別の車に切り替わります（3 回まで）
3. 照準を車に合わせて **[Enter]** で乗車します（迎車の途中でも、近づけば乗れます）
4. 目的地に着いたら **[Enter]** で降車します

| 操作 | 何が起きるか |
|---|---|
| 3D 画面をクリック | マウスで視線を回せる（**[Esc]** で解除）|
| **W / S**・**A / D** | 前進・後退・左右への平行移動 |
| **[Enter]** | 照準に入っている車に乗車／降車 |
| **[Space]** | 緊急停止（その場で止めて自動運転を終える。乗車中なら降ろされる）|

- 実用モードの間は、**街の車もタクシーもすべて、方策ではなく経路追従で走ります**（学習の進み具合に関わらず
  迎えに来させるため）。信号・規制速度・車間はそのまま守ります
- スマホ画面の **カメラ** で、タクシーの車載カメラの映像と認識結果の枠を見られます
- 街の車はすべてタクシーの姿になり、屋根の表示灯と、空車／迎車／賃走／支払の表示が出ます
- 配車は同時に 1 件だけです。エリアの切り替えは開発モードの「マップ」タブから行います
- 金沢ではまれに車どうしが接触します（200 秒・8 台で 2 回ほど。経路の作り方の問題で、実用モードのせいではありません）

- **頼んでも信号・制限速度・車間は緩みません。** Gemini が選べるのは「走り方の切り替え」「緊急停止」「状況の説明」の 3 つだけです

## 画像認識で運転する

車両に渡すのは、**カメラで認識したもの**（信号の灯色・規制速度・車線・車両・障害物・歩行者・走行可能領域）と、
**車載センサーとナビの値**（自車の速度と舵角・目的地の相対位置・経路案内）だけです。**観測はカメラ由来、
報酬と終了条件は真値由来**なので、霧で赤信号を見落として進めば、そのとおり信号無視の罰が入ります。

| 認識器 | 内容 |
|---|---|
| フレームワーク | Keras 3（torch バックエンド。TensorFlow は入れていません）|
| 推論の動かし先 | openvino が入っていれば NPU（Intel AI Boost など）→ 無ければ OpenVINO の CPU。入っていなければ従来の Keras の CPU（下の「NPU で速く動かす」）|
| 入力 | 192×144 の擬似カメラ画像（前方・後方・左・右の 4 台。numpy で描く）|
| 出力 | 6×8 グリッドの検出（12 クラス・灯色・規制速度・距離・指定方向など）と走行可能領域。クラスの出典は `percep/types.py` の `DetClass`、出力幅は `percep/detector.py` の `CHANNELS`。変更時はこの表も更新 |
| 規模 | 幅の設定で変わります。パラメータ数の出典は `percep/detector.py` の `build_detector(...).count_params()` |

- **雨は画を濁らせるだけ、霧は視程を縮めます。** 視程の外のものは正解ラベルからも外れます（擬似カメラと正解ラベルは同じ視程を使う）
- 運転席カメラにすると、認識したものに枠・名称・推定距離が重なります。**枠はそのまま強化学習の入力**で、画面用に
  描き直していません（認識が外れていれば、そのとおり外れて見える）。車線だけは路面に帯で描きます
- 認識器を Keras の CPU で動かすと、擬似カメラの描画と推論で 1 ステップが 50ms 前後かそれ以上かかります（銀座・8 台。真値で走らせると 10ms 前後）。
  そのため**車両は 8 台が上限**で、倍速は等倍前後で頭打ちになります。NPU で推論を短縮できますが、地図と負荷によって 50ms を超えます（次の節）
- **死角もカメラだけで推定します**（`percep/occlusion.py`）。4 台のカメラの画角を 35 本の方位に分け、走行可能距離
  （建物まで）と検出した車両の陰から「どこまで見えているか」を作ります。地図の建物は直接見ません。左右の見通し距離・
  前の車に隠された割合・遮蔽の角までの距離・前後左右の見えている割合を観測の死角の欄に入れ、**見通しの悪い交差点では
  交差道路がある側の見通しが 20m 開けるまで、入口でクリープ速度（1.2m/s）まで落として車頭をゆっくり出します**
  （経路追従の車。介入の表示は「見通しの悪い交差点」）。「表示」タブの「カメラの視野コーン」「死角シャドウ」を ON にすると、
  追従・運転席カメラで追っている車のものが路面に重なります

### NPU で速く動かす

標準セットアップには `openvino` が含まれ、認識器の推論を **NPU（Intel AI Boost などの OpenVINO 対応アクセラレータ）** へ移します。
NPU が無ければ OpenVINO の CPU で動かし、どちらでも駄目なら従来の Keras の CPU に戻ります（理由はログに残ります）。
**内蔵 GPU は選びません**（ブラウザの 3D 描画とメモリ帯域を取り合うため）。

```powershell
cd backend
.venv\Scripts\python.exe export_openvino.py --bench   # 変換して、Keras / OpenVINO CPU / NPU の速さと差を測る（任意）
```

- 変換は自動です。サーバーが認識器を読むとき・「モデル作成」タブで学習し終えたときに、`data/detector/` へ
  OpenVINO の IR（`detector.ir1-<指紋>.xml` / `.bin`）を作ります。2 回目からは Keras を読まずに IR から 0.3 秒ほどで載ります
- 動かし先は `.env` の `DRIVERL_PERCEP_DEVICE` で選べます（`auto` = NPU → CPU / `cpu` = OpenVINO の CPU / `keras` = 従来どおり）
- NPU は fp16 で計算するので、出力は Keras と少しだけ違います（検出の一致 99.8〜99.9%・距離の差は中央値 2cm 弱）。
  OpenVINO の CPU は fp32 で、検出は Keras と完全に一致します

実測（Core Ultra 7 155H・8 台・全車が経路追従・歩行者 16 人。同じプロセスで動かし先を切り替えながら 100 ステップ × 3 回）:

| | Keras CPU | OpenVINO CPU | OpenVINO NPU |
|---|---|---|---|
| 銀座の 1 ステップ（最小）| 75.4〜79.9ms | 36.9〜48.1ms | **32.7〜33.6ms** |
| 金沢の 1 ステップ（最小）| 77.6ms | 46.7ms | **35.8ms** |
| 推論 1 回（11 枚。前方 8 + 周囲 3）| 約 45ms | 約 20ms | **約 9ms** |
| 1 ステップに使う CPU 時間（全スレッドの合計・銀座）| 1,105ms | 146ms | **22ms** |
| 検出の一致（Keras が基準。晴れ・雨・霧）| — | 100% | 銀座 99.94% / 金沢 99.83% |

### 認識器を学習する

最初は認識器が無いので、真値から作った「理想の検出結果」で代用して走ります。「モデル作成」タブで集める枚数・
エポック数・バッチサイズ・モデルの大きさを決めて **収集して学習を開始** を押すと、教師データの収集から学習・保存・
載せ替えまで完結します（サーバーの再起動は要りません）。

- 集める前に**いまの認識器を採点し、成績の低いクラス・天候を多めに集めます**（アクティブラーニング）。
  銀座 2,400 枚では霧の成績が 11.5% → 71.3% に上がる代わりに、晴れが 79.4% → 65.1% に下がります。天候を混ぜるなら枚数も増やしてください
- 実行中は走行も強化学習も止まり、エリアも変えられません。中止した場合、それまでの認識器はそのまま残ります
- 収集後に出る**クラスの内訳に 0 件のクラス**があると、そのクラスは検出できるようになりません（画面にも警告が出ます）
- 同じ学習は CLI からもできます（中身は同じ実装）。**サーバーを止めてから**回してください

```powershell
cd backend
.venv\Scripts\python.exe train_detector.py --preset ginza --samples 2400 --epochs 12 --batch-size 32 --width 1.0
# 収集だけ: --collect-only / 学習だけ: --train-only / 晴れだけ: --no-weather / 採点を飛ばす: --no-focus
```

## 走行のルール（日本の道路交通法）

経路そのものを車線に沿って作るので、強化学習の側は経路を追うだけで車線を守れます。

| ルール | 根拠 | 実装 |
|---|---|---|
| 左側通行・一番左の車線 | 17 条 4 項・20 条 1 項 | 対面通行路では左半分の車線を使い、既定で最も左の車線を通る |
| 右左折時の寄せ | 34 条 | 左折は左端の車線のまま、右折は 35m 手前から最も右の車線へ移る |
| 赤信号で停止線を越えない | 施行令 2 条 | 停止線の手前で止まれる速度に抑える。越えると罰（既定 -60）|
| 最高速度を超えない | 22 条 1 項 | 道路ごとの規制速度（OSM の `maxspeed`、無ければ道路種別の既定値）を超えない。超えると罰（既定 -5）|

- 信号と標識は、指令を書き換えるのではなく**速度の上限という環境の性質**として掛けます。「シミュレーション」タブの
  **信号に従う** / **標識に従う** を切ると罰だけが残り、守れるかは学習しだいになります
- 信号は青 → 黄 → 全赤で交代し、**交差する流れが同時に青になることはありません**（サイクル 60 秒を現示の数で分け合う）。
  歩行者用信号は車両信号の裏返しで、歩行者は赤のうちは渡り始めません
- 最高速度標識は規制速度が変わる進入口にだけ立てます。道路標示は「道路標識、区画線及び道路標示に関する命令」の寸法に
  合わせています（追越し禁止の黄色実線は OSM から判別できないので描きません）
- 一時停止・横断歩道・一方通行・指定方向外進行禁止・駐車禁止・駐停車禁止の標識も、地図から抽出して表示し、CNN が別々のクラスとして認識します。
  指定方向の矢印も認識し、その結果を PPO の観測末尾へ追加します。新標識に対応する教師データは収集し直して認識器を学習してください。
  OSM の標識タグや規制タグから作るため実地の標識を網羅しません。一時停止の進入方向が特定できない場合は、ログを残して配置を省略します。
- 新標識追加後の金沢の速度検証（2026-10-08、旧キャッシュをメモリ上で変換、8 台・歩行者 16 人、PPO 更新と配信を除く）では、
  真値モードの中央値 27.01ms／p95 54.72ms、未学習 CNN の OpenVINO NPU は 49.70ms／61.56ms でした。
  **50ms 以内を常に満たすことは確認できていません。** 条件と比較値の出典は CLAUDE.md「新標識の認識と観測」です。認識精度を示す値ではありません。
- 実装していないこと: 停止車両の追い越し、新標識に対する自動停止や違反罰の追加、右折時の対向車優先

## 学習したモデルを書き出す・読み込む

「学習」タブ →「モデルの書き出し」から 4 つの形式でダウンロードできます（学習は止まりません）。
どれにも、観測ベクトルの内訳と行動のスケールがメタデータとして入っています（次元の出典は `config.OBS_DIM`）。

| 形式 | 使いみち |
|---|---|
| 重み一式（`.pt`）| 「モデルの読み込み」で戻すと、続きから学習を再開できる |
| torch.export（`.pt2`）| このリポジトリのコード無しで推論できる。PyTorch が TorchScript の後継として勧める形式 |
| TorchScript（`.torchscript.pt`）| このリポジトリのコード無しで推論できる。PyTorch が非推奨にしたので、新しく使うなら `.pt2` |
| Keras（`.keras`）| Keras 3 のモデルとして扱える（`custom_objects` 不要。`KERAS_BACKEND=torch` で読める）|

```python
import json, torch

extra = {"metadata.json": ""}
policy = torch.export.load("<書き出したファイル>.pt2", extra_files=extra).module()
meta = json.loads(extra["metadata.json"])
print(meta["observation"]["layout"])            # 観測の内訳

obs = torch.zeros(1, meta["model"]["obsDim"])   # 次元はメタデータから読む
action, value = policy(obs)                     # action: (B, 2) = 加減速・操舵（-1〜1）
```

TorchScript 版なら `policy = torch.jit.load("<書き出したファイル>.torchscript.pt", _extra_files=extra)` で、あとは同じです。

- 読み込む前に、それまでの重みを `backend/data/exports/` へ自動で退避します（退避できなければ読み込みません）。
  `exports/` には書き出しを 20 世代、退避を 10 世代まで残します
- torch.export 版・TorchScript 版・Keras 版は推論専用で、学習の再開には使えません
- torch.export 版はモデルをトレースするので、書き出す間（1 秒足らず）シミュレーションが止まります
- `.pt` は必ず `weights_only=True` で解析し、テンソルと素の値以外が入っていれば読み込みを止めます（詳しくは `SECURITY.md`）
- 読み込みはファイル 1 つ、256MiB までです（出典: `backend/app/model_upload.py`）。受信中に容量を検査し、超過した部分ファイルも片付けます
- 書き出しは JSON の POST です。以前の GET では生成しません
- 容量検査は HTTP 側で行います。2026-10-09 の新旧比較でファイル内容は一致し、2MiB の解析は中央値 13.9 → 14.5ms でした（計測条件は `CLAUDE.md`「モデルの入出力」）
- コマンドラインからは `curl.exe -OJ -H "Content-Type: application/json" -d "{}" http://127.0.0.1:8000/api/export/checkpoint`（`pt2` / `torchscript` / `keras`）で取れます

## ハイパーパラメータを自動で探す（学習の自動化）

「学習」タブの一番下の **学習の自動化（Optuna）** を ON にすると、学習率・割引率・クリップ範囲・エントロピー係数と
報酬の重み（目的地到達・衝突・経路進捗・道路外・信号無視・速度超過・時間）の 11 個を、Optuna（TPE）が試行を繰り返して探します。

- 1 試行ごとに、重みを **ON にしたときの状態へ巻き戻し、街を作り直してから** 76.8 秒ぶん（1,536 ステップ）学習させ、
  後半の走り（到達・衝突・逸脱・打ち切り・信号無視・止まったままでないか）で採点します。報酬の重みも探すので、
  **採点に報酬の合計は使いません**。見込みの薄い試行は途中で打ち切ります
- 探索中は、試行が替わるたびに上のスライダーがその値へ動きます（「自動」の印が付き、手では動かせません）。
  保存・読み込み・初期化・エリアの切り替え・実用モード・認識器の学習も、OFF にするまでできません
- **OFF にした瞬間**に、元の重みを `backend/data/checkpoints/shared_policy.pt.before-autotune` へ退避してから、
  この探索で最も成績の良かった試行の設定と重みを適用して `shared_policy.pt` に保存し、そのまま学習を続けます。
  完了した試行が無ければ、ON にする前の設定と重みに戻ります
- 気に入らなければ、「モデルの読み込み」で `shared_policy.pt.before-autotune` を選べば戻せます
- 学習タブの設定値（学習率・報酬の重み・スイッチ）は変えるたびに `backend/data/learning_params.json` へ自動で保存され、
  再起動しても戻ります。探索中の試行の値は保存せず、OFF にして最良の試行が確定したときに保存します。
  最良の値は `backend/data/tuning/best_params.json` にも残ります
- 1 試行は実時間で約 77 秒（倍速を上げれば短くなる）。TPE が当たりを付け始めるまでに 10 試行ほどかかります

| 保存先（`backend/data/` の下）| 中身 |
|---|---|
| `learning_params.json` | 学習タブの設定値の控え（起動時に戻す。消すと既定から始まる）|
| `tuning/driverl_optuna.db` | 探索の履歴（SQLite・WAL）。同じ study 名で続きから探す（画面からはエリアごとに `live-<エリア>`）|
| `tuning/best_params.json` | 最良の試行の値（`set_params` と同じキー）|
| `tuning/trial_summary.csv` | 試行ごとの値と成績の一覧 |
| `checkpoints/best_tuned_policy.pt` | 最良の試行の重み（本番の `shared_policy.pt` とは別）|

同じ探索はサーバーを使わず CLI でも回せます（中身は同じ実装。本番の `shared_policy.pt` は読むだけで書き換えません）。

```powershell
cd backend
.venv\Scripts\python.exe tune_hyperparams.py --preset ginza --trials 20
# 1 試行の長さ: --trial-steps 3072 / 続きから: 同じ --study-name（既定 cli-<preset>）/ 初期値から: --init fresh
# 地図のキャッシュを読まない短い動作確認: --preset grid --trials 2 --trial-steps 128
.venv\Scripts\optuna-dashboard.exe sqlite:///data/tuning/driverl_optuna.db   # 履歴をブラウザで見る（要 requirements-dev.txt）
```

## 設計上の要点

| 項目 | 方針 |
|---|---|
| 学習 | オンライン学習。最大 8 台が 1 つの重みを共有する（parameter sharing）|
| 観測 | 111 次元（カメラ認識・周囲カメラ・センサーとナビ・V2X・死角・新標識）。次元と内訳の出典は `backend/app/config.py` の `OBS_LAYOUT`。変更時はこの表も更新 |

| 報酬 | 目的地到達・衝突回避・経路進捗・信号順守・最高速度順守 |
| 物理 | 詳細な動的自転車モデルを常時使用。衝突はバックエンドで判定する |
| 実行 | 物理と PPO は専用スレッドで 20Hz（1 ステップの予算 50ms）。ブラウザは 60fps で補間して描く |
| 通信 | WebSocket（状態の配信・操作）+ HTTP（モデルの入出力・AI コンシェルジュ）。契約は `docs/protocol.md` |
| 永続化 | PPO の重みとオプティマイザの状態を自動で保存し、次の起動で戻す |

## つまずきやすい点

| 症状 | 原因と対処 |
|---|---|
| 名前（`mypc.local` など）で開くと 403 | DNS リバインディング対策です。`.env` の `DRIVERL_ALLOWED_HOSTS` に名前を書いて起動し直してください（IP アドレスで開くなら不要。`SECURITY.md` の 5）|
| マップの読み込みが終わらない | Overpass API の混雑が多い原因です。時間をおいて `python -m app.map.prefetch` を再実行してください |
| `ポートが既に使われています` / `5173 is in use` | 前回の起動が残っています。表示された `taskkill` の行を実行するか、`Get-Process node` → `Stop-Process -Id <PID>` で片付けてください |
| 本当に学習しているか分からない | 「学習」タブのノード図で、点が脈打ち、勾配と Δ が 0 でなければ重みは動いています |
| 動きがランダムに見える | エントロピーを見てください。行動は 2 次元なので、探索の広さが健全なら **1.8 前後**です（初期値の探索ノイズ 0.6 に対応。下がること自体は異常ではない）。4.8 近くまで上がっていたら方策が潰れているので「ポリシーを初期化」でやり直してください |
| どの車も止まったまま動かない | 方策が「止まる」に固まっています。**サーバーを止めてから** `backend` で `.venv\Scripts\python.exe warmstart_policy.py --preset ginza` を回すと、方策・価値関数・探索の幅を立て直します（元の重みは `shared_policy.pt.before-warmstart` に残ります）|
| 動きがぎこちない・信号を無視する | 学習の初期は正常です。「学習」タブの到達率と信号無視の推移で進み具合を見てください |
| 速度超過が 0 のまま | 「標識に従う」が有効なら正常です（環境が超えさせないため）|
| フレームレートが出ない | 「表示」タブでまず影を切ってください。道路標示・信号機も切れます |
| 道路や路面がちらつく | 深度の精度不足（Z ファイティング）です。`RoadNetwork.tsx` / `RoadMarkings.tsx` の `polygonOffset` の順を確かめてください |
| 隠れ層の構成を変えたい | 「学習」タブで層の数（1〜4）と幅を選べます。重みは引き継げないので、先に書き出しておいてください |
| 学習の自動化のトグルが押せない | カードの下に理由が出ます。Optuna が無ければ `pip install -r requirements.txt` の後にサーバーを起動し直してください。マップを読み込む前・実用モード・認識器の学習中も始められません |
| 学習の自動化の後の走りが気に入らない | 「モデルの読み込み」で `backend/data/checkpoints/shared_policy.pt.before-autotune` を選ぶと、ON にする前の重みに戻ります |
| 学習をやり直したい | 「学習」タブの「ポリシーを初期化」を使ってください |
| 以前のモデルが読み込めない | 観測の次元が変わったためです（50 → 54 → 56 → 57 → 66 → 75 → 79 → 87 → 111）。66・75・79・87 次元の PPO の重みは、入力を 0 で足して読み込めます。旧 CNN はクラスと出力の形が異なるため、教師データの収集と学習が必要です |
| 認識結果の枠が出ない | カメラが「運転席」か、「表示」タブのスイッチ、追跡している車があるかを確かめてください |
| 認識器が何も検出しない | 収集後のクラスの内訳に 0 件のクラスが無いか、学習の最後の検証時の検出数を見てください。枚数とエポックを増やすのも有効です |
| 認識器の学習中に車が止まった | 仕様です（CPU を使い切るので物理と PPO を止める）。完了・中断すると自動で再開します |
| 認識器を入れたら遅くなった | Keras の CPU では仕組み上そうなります。`requirements.txt` の依存を更新して NPU / OpenVINO を使えるか確認するか（「NPU で速く動かす」）、モデルの大きさを 0.5 倍にして学習し直してください（CLI なら `--width 0.5`）|
| NPU で動いていない | 起動ログの「認識器を … で動かします」を見てください。`openvino` が入っていない・`.env` の `DRIVERL_PERCEP_DEVICE` が `cpu` / `keras`・NPU のドライバが無い、のどれかです。`export_openvino.py --bench` でデバイスの一覧が出ます |
